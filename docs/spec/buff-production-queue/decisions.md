# Decisions (ADR): `produce_buff`

> Отклонение от любого ADR без обновления этого файла запрещено
> (`docs/spec/constitution.md` §1).

---

## ADR-1. Очередь производства моделируется отдельно от очереди строительства

**Контекст.** Оператор поставил это условием: строительство зданий и
производство эффектов — разные очереди.

**Решение.** Подтверждено кодом игры и принято. См. `data-sources.md` §5.1:
два разных класса (`cBuildQueue` против `cTimedProductionQueue`), разные владельцы
(игрок против зоны), разные наборы команд (115–117 против 1025–1030).
Заказ бафа не занимает слот стройки.

**Следствие.** Никакого кода, читающего или пишущего `mBuildQueue`, в этой фиче нет.
Логика `build_mine` / `upgrade_mine` (которая КАСАЕТСЯ очереди стройки)
не переиспользуется и не служит образцом для расчёта слотов.

## ADR-2. Ключ очереди — `productionType`, а не grid здания

**Контекст.** Гипотеза оператора: у каждого здания своя собственная очередь.

**Найденный факт.** Гипотеза верна лишь частично. `client_scripts.txt:331321`
и `78279–78285` показывают: очередь живёт в `cZone.productionQueue_vector`
и ищется по `mProductionType`. Здание ПЕРЕИСПОЛЬЗУЕТ существующую очередь своего
типа, если такая в зоне есть.

**Решение.** Моделируем как есть в игре: ключ `(zone, productionType)`.

**Обоснование.** С точки зрения оператора разница проявляется только при двух
зданиях одного типа — тогда они делят очередь. Если смоделировать по grid,
система будет считать слоты вдвое больше, чем есть, и будет молча терять заказы.
Игра сама предупреждает об этом ключом `"DuplicatedBuildingTimedProductionTip"`
(`client_scripts.txt:307464`).

**Отвергнуто.** Модель «очередь на grid» — проще в UI, но врёт оператору.

**Следствие.** INV-5. Плюс FR-11: UI обязан показать `shares_queue_with`.

## ADR-3-R. Один шаг = один вызов с `amount`, а не N шагов

> **Ревизия.** Исходный ADR-3 утверждал, что VO несёт только 5 полей.
> Живой трафик это **опроверг**: по проводу идут все **14 полей** VO,
> три из них — `double` (P-22). Клиент заполняет пять значащих, остальные
> едут со значениями по умолчанию — но едут всегда, и порядок traits
> жёсткий. См. `protocol-evidence.md` §1. Само решение про `amount` осталось
> в силе и подтвердилось.

**Контекст.** В `collect-building` ADR-9 и `build-mine` ADR-6 мультивыбор
разворачивается в N отдельных атомарных шагов. Естественно было бы повторить.

**Решение.** Не повторяем. «10 бафов» — ОДИН шаг с `amount: 10`.

**Обоснование.** Протокол игры сам несёт `amount`. `client_scripts.txt:307965`
берёт его из слайдера (`amountSlider.value`). Разворачивание в 10 вызовов было бы
10-кратным перерасходом сетевых вызовов и дало бы 10 точек частичного отказа
вместо одного атомарного решения сервера.

**Почему это не противоречит прецедентам.** Там разворачивание было вынужденным:
команды 13002 и 50 принимают ровно один grid и не имеют поля количества.
Здесь поле есть. Мы следуем протоколу, а не шаблону.

**Следствие.** AC-4. Мультивыбор НЕСКОЛЬКИХ РАЗНЫХ рецептов всё же
разворачивается в N шагов — по одному на рецепт, так как VO несёт один
`type_string`.

**Следствие ревизии (обязательно к исполнению).** PHP-класс VO объявляет
все 14 свойств в точном порядке: `uniqueId`, `playerId`, `productionType`,
`type_string`, `amount`, `producedItems`, `collectedTime`,
`modifiedProductionAdder`, `modifiedProductionMultiplier`,
`modifiedInstantFinishCostAdder`, `modifiedInstantFinishCostMultiplier`,
`stacks`, `index`, `buildingGrid`. Значения по умолчанию при отправке:
`uniqueId = null`, `playerId = 0`, `producedItems = 0`, `collectedTime = 0.0`,
аддитивы `0`, мультипликаторы `1.0`, `index = 0`.
Убирать «лишние» поля нельзя — сервер ждёт полные traits.

## ADR-4. Одно здание на шаг, без мультивыбора зданий

**Решение.** Шаг `produce_buff` ссылается ровно на одно здание (один `grid`).

**Обоснование.** Из-за ADR-2 мультивыбор зданий вводит в заблуждение: выбрав
два ProvisionHouse, оператор ожидает две независимые очереди, а получает одну.
Разные типы зданий имеют разные наборы рецептов, так что общий выбор рецепта
для них невозможен. Мультивыбор зданий здесь лишён смысла.

**Отличие от `task-planner-multi-select`.** Там мультивыбор был осмыслен, потому
что действие (примени��ь баф, собрать) однородно для всех выбранных целей.
Здесь нет.

**Мультивыбор РЕЦЕПТОВ — разрешён.** В пределах одного здания оператор может
выбрать несколько рецептов; каждый становится отдельным шагом (ADR-3).

## ADR-5. Каталоги — в конфиге, генерируются artisan-командой

**Решение.** Каталог зданий (68) и рецептов (299+) живёт в `config/game.php`
под ключом `game.production`. Заполняется командой
`php artisan tso:import-production-catalog`, читающей `docs/references/icons.xml`
и `docs/references/globals.xml`.

**Обоснование.** Прецедент `build-mine` ADR-4 (игровые данные в `config/game.php`)
и follow-up F-5 там же (генерировать командой, а не вести руками). Здесь
объём данных (367 записей со вложенными стоимостями) делает ручное ведение
нереалистичным — генератор обязателен сразу, а не в follow-up.

**Отвергнуто.**
- Парсить XML в рантайме — 4.3 МБ на каждый запрос неприемлемо.
- Таблица БД — данные статичны, меняются только с патчем игры; миграции и
  сиды — лишняя сложность.

**Следствие.** INV-6. Команда идемпотентна, и её вывод коммитится в git,
чтобы diff был виден при обновлении игры.

## ADR-6. Стоимость — снапшот на момент планирования

**Решение.** Рассчитанная стоимость пишется в `meta.cost` шага при добавлении
в sequence и больше не пересчитывается. При исполнении используется только для
лога, НЕ для решений.

**Обоснование.** Аналог — `collect-building` ADR-6 и `build-mine` ADR-8: `meta` есть
презентационный слепок, не источник истины. Стоимости в игре могут поменяться
патчем между планированием и исполнением; решать всё равно будет сервер игры.

**Следствие.** Нельзя отклонять шаг на основании расхождения `meta.cost`
с текущим каталогом. Можно только логировать предупреждение.

## ADR-7. Отказ политики — успешный исход, не исключение

**Решение.** Невозможность поставить заказ (очередь занята, здание в апгрейде,
здание исчезло, рецепт стал недоступен) — это **успешно завершённый шаг**
с локализованной строкой-причиной. Не исключение, не `status: failed`.

**Обоснование.** Прямой прецедент `build-mine` ADR-12. Иначе один шаг в середине
большой sequence валит всю задачу и забивает лог нормальной игровой ситуацией.
Согласовано с оператором в диалоге.

**Исключения.** Исключения остаются только для технических сбоев: сеть, авторизация,
невалидный AMF-ответ. Они идут через существующие `ActionRetryPolicy` и
`GameResponseValidator`.

**Перечень причин отказа (enum `ProductionRejectionReason`).**

| Значение | Когда |
| --- | --- |
| `BuildingNotFound` | grid отсутствует в свежем снапшоте |
| `NotAProducer` | у здания `productionType` отсутствует или `< 0` |
| `ProductionTypeMismatch` | `productionType` в payload не совпал со снапшотом |
| `QueueDataUnavailable` | снапшот не дал содержимого очереди (INV-4) |
| `QueueFull` | в очереди нет места под заказ |
| `RecipeUnknown` | `recipe_name` нет в каталоге для этого `productionType` |
| `RecipeLevelLocked` | уровень здания вне `requiresUpgradeLevelMin..Max` |
| `BuildingUpgrading` | здание в процессе апгрейда |

## ADR-8. Рецепты с событийными требованиями показываются с пометкой, а не скрываются

**Контекст.** Оператор выбрал строгую фильтрацию («как честнее»). Но клиент игры
проверяет три вещи: `group`, уровень здания и
`RequirementsHelper.checkRequirements(requiresEvent, requiresQuest)`. Первые две мы
можем воспроизвести точно. Третью — нет: активные события и статусы квестов
в снапшоте не представлены.

**Решение.** Рецепты с непустыми `requiresEvent` / `requiresQuest` получают
`availability: "unknown"` и показываются с визуальной пометкой.
Рецепты без таких требований — `availability: "available"`.

**Почему не скрывать.** Событийные рецепты — часто самое ценное, что есть
в бафовом здании. Скрыв их из-за собственного неведения, мы молча лишим
оператора функционала без всякой диагностики. Показать с пометкой — честнее,
чем скрыть: мы явно сообщаем границу своего знания. Сервер игры остаётся
авторитетом: если событие не идёт, он отклонит заказ и шаг завершится по ADR-7.

**Совместимость с FR-6.1.** Уровневой фильтр СКРЫВАЕТ рецепт, так как там у нас
есть достоверные данные. Разница в поведении намеренная: скрываем только то,
в недоступности чего уверены.

## ADR-9. `stacks` всегда равен 1, но передаётся явно

**Решение.** Поле `stacks` всегда заполняется значением `1` и НЕ выносится в UI.
В payload шага оно присутствует явно.

**Обоснование.** Три из четырёх мест вызова в клиенте шлют `stacks = 1`.
Стакинг зависит от `productionQueue.hasStackingBonus`, который выводится из
`GetGOContainer().stackingBuffs_vector.length > 0` (`client_scripts.txt:78284`) — этого
данного в снапшоте нет. Ставить `stacks > 1` вслепую — нарушение INV-4.

**Почему поле всё равно в payload.** Чтобы будущее включение стакинга не меняло
формат сохранённых задач (без миграции payload).

**Follow-up F-4.** Если потребуется стакинг — сначала добавить
`has_stacking_bonus` в снапшот, потом открывать поле в UI.

## ADR-10. Свежий снапшот обязателен, кеш `Account::$zone_data` запрещён

**Решение.** Хендлер всегда запрашивает зону через
`ZoneSnapshotProviderInterface`, не читая `Account::$zone_data`.

**Обоснование.** Прямые прецеденты: `build-mine` ADR-5 и `collect-building` ADR-10.
Задачи исполняются по расписанию спустя часы после планирования; очередь и
уровни зданий к этому моменту гарантированно устарели.

**Следствие.** Один запрос зоны на шаг. Для sequence из N шагов по одному аккаунту
допускается кеш в пределах ОДНОГО исполнения таски, но **с инвалидацией после
каждого успешного заказа** — иначе второй шаг увидит устаревшее состояние
очереди и переполнит её.

## ADR-11. Архитектура обобщается на любой `productionType`, UI — только бафы

**Решение.** Бэкенд (VO, шлюз, хендлер, политика, калькулятор) не содержит
проверок вида `productionType === 1`. Ограничение «только бафы» живёт
исключительно в конфиге каталога и в фильтре API-эндпоинта.

**Обоснование.** Команда 91 и VO идентичны для юнитов, навыков, эффектов и
коллекций — все четыре места вызова в клиенте используют одну форму. Зашивать
«бафовость» в протокольный слой значит гарантированно переписывать его при
следующей фиче.

**Граница.** Это НЕ разрешение реализовать производство юнитов сейчас
(см. Out of scope №4). Запрещено добавлять код «на будущее» под те типы,
которые не покрыты тестами (`constitution.md` §5 — нет мёртвого кода).

## ADR-12. Шлюз вместо прямого `TsoAmfService` в хендлере

**Решение.** Вводится `ProductionCommandGatewayInterface` с одним методом
`queueOrder(...)`. Реализация `AmfProductionCommandGateway` делегирует в
`TsoAmfService`.

**Обоснование.** Прямой прецедент `build-mine` ADR-9 (там
`MineCommandGatewayInterface` / `AmfMineCommandGateway`). Даёт тестируемость без
моканья 13-килобайтного сервиса.

**Следствие.** INV-7. Регистрация — в `TaskServiceProvider`, рядом с
существующими биндингами.

## ADR-13. Расширение снапшота — аддитивное, без изменения существующих ключей

**Контекст.** `ZoneSnapshot` и `ZoneParserService` используются всеми фичами
проекта. Оператор подтвердил расширение парсера.

**Решение.** Только добавление новых ключей. Запрещено:
переименовывать существующие ключи, менять типы существующих значений,
менять форму `buildings[]`. Новые ключи должны быть nullable, чтобы старые
закешированные снапшоты продолжали работать.

**Следствие.** Старый снапшот без новых ключей ведёт к `QueueDataUnavailable`
по INV-4, а не к падению. Обязателен регресс-тест на старую фикстуру зоны.

## Открытые вопросы (требуют решения ДО реализации)

> **Статус на версию пакета 2.0.** OQ-1, OQ-2, OQ-3 ЗАКРЫТЫ — разбор и
> решения в `oq-resolutions.md`. Остальной текст раздела сохранён как
> история вопроса. Открытыми остаются только OQ-4 (байт-в-байт ЗАПРОС
> команды 91) и OQ-5 (семантика `collectedTime`); ни один из них не блокирует
> реализацию.

### OQ-1. Точное условие выбора механизма каталога

См. `data-sources.md` §6.3. Нужно дочитать `client_scripts.txt:307900–307940`
и зафиксировать точное условие `if`, разделяющее ветки
`global.timedProductions_vector[type]` и `cBuff.GetProduceableBuffDefinitions()`.
Гипотеза: `!TIMED_PRODUCTION_TYPE.isHardcoded(mProductionType)`.
Блокер для этапа 1 из `implementation-plan.md`.

### OQ-2. Максимальный размер очереди производства

`cTimedProductionQueue` не содержит поля `mMaxCount` (в отличие от `cBuildQueue`,
где `mMaxCount = 3`). Где задан лимит — не найдено. Вероятно, лимит
серверный либо зависит от уровня здания.

**Временное решение до выяснения.** Не отклонять заказ по собственному
расчёту лимита. `QueueFull` выставлять только когда сервер игры сам отказал.
В UI показывать текущее число заказов без знаменателя («в очереди: 3», а не
«3/6»). Запрещено выдумывать лимит вида «наверное, 6».

### OQ-3. Конфликт версий в документации проекта (вне этой фичи)

`docs/spec/constitution.md` §3 требует PHP ^8.5 / Laravel ^12.0 и
`./vendor/bin/pint --test`. `docs/spec/laravel-constitution.md` заявляет php 8.1.9 /
Laravel v10 / Sanctum v3, `pint --dirty`, PHPUnit вместо Pest и `protected $casts = []`
вместо `casts()`.

По §1 `constitution.md` при конфликте источников надо остановиться и вынести
конфликт. Формально выношу здесь. Для данного спека принято:
`constitution.md` имеет приоритет (он выше в иерархии и согласуется с
`php-85-upgrade/`). Окончательное решение — за оператором.
