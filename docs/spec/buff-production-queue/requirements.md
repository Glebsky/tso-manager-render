# Requirements: `produce_buff`

## Глоссарий

| Термин | Определение |
| --- | --- |
| **Здание-производитель** | Здание с `productionType >= 0` в `icons.xml`. Всего 68. |
| **Рецепт** | Запись `<Buff produceable="true">` или `<TimedProduction>`. Имеет `name`, `group`, длительность, `<Costs>`. |
| **Очередь производства** | `cTimedProductionQueue`, одна на пару (зона, `productionType`). **Не путать с очередью строительства.** |
| **Заказ** | Одна единица `dTimedProductionVO`: рецепт + `amount` + `stacks` + `buildingGrid`. |
| **Шаг** | Элемент `payload.actions[]` задачи типа `sequence`. |
| **Снапшот стоимости** | Зафиксированная на момент планирования стоимость в `meta.cost`. |

---

## Функциональные требования

### FR-1. Новый тип задачи `produce_buff`

Добавляется `TaskType::ProduceBuff = 'produce_buff'` — атомарный тип действия,
применимый как шаг `sequence` и как самостоятельная задача.

### FR-2. Каталог зданий-производителей

Система знает соответствие `building_name -> productionType` для всех 68 зданий
из `icons.xml` (см. `data-sources.md` §4.1).

### FR-3. Каталог рецептов

Система знает для каждого рецепта: `name`, `group`, длительность в секундах,
`<Costs>`, `requiresUpgradeLevelMin/Max`, `requiresEvent`, `requiresQuest`,
к какому `productionType` он относится.

### FR-4. Расширение снапшота зоны

Источник и точные имена полей — `zone-snapshot-evidence.md`, схема ключей —
`design.md` §4. Всё ниже подтверждено живым снапшотом, а не предположениями.

- **FR-4.1** `production_type` у каждого здания (или `null`). Значение берётся
  из статичного каталога по `buildingName_string`. В AMF-снапшоте такого поля
  НЕТ — поэтому каталог (FR-2) блокирует это требование.
- **FR-4.2** `upgrade_level` (AMF `upgradeLevel`), `upgrade_in_progress`
  (AMF `upgradeIsInProgress`), `production_active` (AMF `isProductionActive`).
- **FR-4.3** содержимое очередей производства зоны из `timedProductions_vector`:
  список очередей, у каждой — `production_type` и список заказов
  (`type_string`, `amount`, `produced_items`, `collected_time`, `stacks`, `index`).

**FR-4.4 (критично).** Очередь сопоставляется с типом только по
`orders[0].productionType`. Индексация по позиции в массиве запрещена (P-26).

**FR-4.5.** Заказы НЕ сопоставляются с конкретным зданием: в снапшоте
`buildingGrid` у заказа равен 0 (P-24). Доступна только занятость очереди
в целом по типу.

Если какое-либо из этих данных не удалось разобрать — см. INV-4.

### FR-5. API списка возможностей

`GET /api/accounts/{account}/buff-producers` возвращает список зданий-производителей
в зоне аккаунта, для каждого:

- `grid`, `building_name`, `building_label` (локализованное), `production_type`,
  `upgrade_level`;
- `queue`: `{ used, orders[] }` — текущее содержимое очереди;
- `shares_queue_with`: массив grid других зданий с тем же `productionType` (FR-11);
- `recipes[]`: доступные рецепты с `name`, `label`, `group`, `duration_seconds`,
  `costs[] = {resource, resource_label, count}`, `availability`, `costs_known`.

### FR-6. Фильтрация рецептов по фактической доступности

Решение оператора: «как честнее». Значит:

- **FR-6.1** рецепты вне диапазона `requiresUpgradeLevelMin..Max` для текущего
  уровня здания **не показываются**;
- **FR-6.2** рецепты чужой `group` не показываются;
- **FR-6.3** рецепты с непустыми `requiresEvent`/`requiresQuest` показываются с
  `availability: "unknown"` и визуальным предупреждением (ADR-8);
- **FR-6.4** рецепты без `<Costs>` (51 шт.) показываются с нулевой стоимостью и
  пометкой `costs_known: false`, а не скрываются.

### FR-7. Планирование в UI

В `Tasks.vue` появляется тип шага `produce_buff`. Поток:

1. оператор выбирает одно здание-производитель (ADR-4 — без мультивыбора зданий);
2. видит список доступных рецептов, сгруппированных по `group`;
3. выбирает рецепт и указывает `amount` (1..МАКС, см. FR-9);
4. видит расчётную стоимость и время (FR-8) **до** добавления;
5. нажимает «добавить» — шаг попадает в `sequenceActions`.

### FR-8. Расчёт стоимости и времени

- **FR-8.1** Стоимость шага = для каждого `<Cost>`: `count × amount × stacks`.
- **FR-8.2** Время шага = `duration_seconds × amount × stacks`.
- **FR-8.3** Стоимость всей sequence = сумма по ресурсам всех шагов `produce_buff`.
  Отображается сводкой над списком шагов.
- **FR-8.4** Снапшот расчёта пишется в `meta.cost` шага и больше не пересчитывается
  (ADR-6). При исполнении служит только для лога.
- **FR-8.5** Если у рецепта `costs_known: false`, его вклад в сводку — ноль, но сводка
  помечается как неполная.

### FR-9. Валидация ввода

- `grid`: `required|integer|min:0`
- `production_type`: `required|integer|min:0`
- `recipe_name`: `required|string|max:120` — должен существовать в каталоге для этого
  `production_type`
- `amount`: `required|integer|min:1|max:100`
- `stacks`: `required|integer|min:1|max:10` (фактически всегда `1`, см. ADR-9)

### FR-10. Исполнение шага

При исполнении шага `produce_buff` система:

1. берёт **свежий** снапшот зоны (кеш `Account::$zone_data` запрещён, ADR-10);
2. проверяет политикой (`ProductionOrderPolicy`), можно ли ставить заказ;
3. если нельзя — возвращает успешный исход с локализованной причиной (ADR-7);
4. если можно — отправляет команду 91 с VO;
5. валидирует ответ через существующий `GameResponseValidator`.

### FR-11. Предупреждение о разделяемой очереди

Если в зоне есть ≥ 2 зданий с одним `productionType`, UI явно сообщает, что они
делят общую очередь. Обоснование — `data-sources.md` §5.3.

### FR-12. Локализация

Все новые строки UI и причины отказа — в `lang/{en,ru,uk}/ui.php`. Имена зданий и
рецептов — из игровой локализации (`data-sources.md` §8).

## Инварианты

> Нарушение любого INV — блокер. Не «технический долг», а блокер.

**INV-1. Формат `payload.actions[]` не меняется.**
Шаг остаётся `{ task_type, payload, delay_seconds, meta }`. Никаких новых ключей
верхнего уровня. Совместимость с `task-planner-multi-select` INV-1.

**INV-2. Существующие типы задач не затронуты.**
`stop_production`, `start_production`, `apply_buff`, `collect_building`, `build_mine`
и прочие работают побайтово так же. Запрещено править `startProduction()` /
`stopProduction()`.

**INV-3. Команда 91 не смешивается с 107.**
Новый код команды — отдельная константа, отдельный метод, отдельный VO.

**INV-4. Fail-safe при неполных данных.**
Если снапшот не даёт `productionType`, уровня здания или содержимого очереди —
действие **запрещается** с явной причиной. Никогда не догадываться и не
отправлять команду «на авось». Аналог — `build-mine` ADR-7.

**INV-5. Очередь ключуется по `productionType`.**
Вся логика подсчёта слотов, идемпотентности и локов использует ключ
`(account_id, production_type)`, НЕ `(account_id, grid)`.

**INV-6. Игровые данные не зашиты в код.**
68 зданий, 299+ рецептов и их стоимости живут в конфиге, сгенерированном из
`docs/references/*.xml`. В PHP-классах нет литералов имён зданий/рецептов.
Совместимость с `build-mine` ADR-4.

**INV-7. Сетевой слой за интерфейсом.**
Хендлер не зависит от `TsoAmfService` напрямую, только от узкого интерфейса.
Совместимость с `build-mine` ADR-9.

## Вне области (Out of scope)

Явно **не** входит в эту версию:

1. Забор готовой продукции (`DELIVER_PRODUCTION = 141`). Отдельная фича (F-1).
2. Сортировка и удаление заказов (1025–1030). Отдельная фича (F-2).
3. Моментальное завершение за гемы (`instantFinishCost`).
4. Производство юнитов (`productionType` 0, 7, 8), навыков (2) и коллекций (4) —
   протокол тот же, но каталоги другие. Архитектура должна это допускать (ADR-11),
   но UI в этой версии показывает только буфовые здания.
5. Проверка достаточности товаров на складе блокирующим образом — только
   информативно (F-3).
6. Производство в зонах друзей.
