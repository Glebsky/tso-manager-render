# Pitfalls: `produce_buff`

Каждый пункт ниже — ошибка, которая была реально совершена или почти совершена
в ходе исследования. Читать ПЕРЕД написанием кода.

---

## P-1. Команда 107 — НЕ то, что нужно

В проекте уже есть `CMD_STOP_PRODUCTION = 107`, методы `startProduction()` и
`stopProduction()`, а также `StartProductionHandler`. Названия выглядят как то,
что нужно. Это ловушка.

Команда 107 — тумблер «шестерёнка вкл/выкл» на шахте и подобных зданиях
(`SendServerAction(107, active ? 1 : 0, grid, 0, null)` — см.
`user_drunken_miner.js:61–64`). Она НИЧЕГО не ставит в очередь.

Нужная команда — **91** (`START_TIMED_PRODUCTION`, `client_scripts.txt:69418`).

Запрещено трогать `startProduction()`/`stopProduction()`/`StartProductionHandler`.
Новый метод называется `queueTimedProduction()` именно чтобы не слиться
с ними по смыслу.

---

## P-2. Команда 91 НЕ использует обёртку `dServerAction`

Все существующие команды проекта (50, 60, 61, 65, 107, 13002) собирают payload
через `buildServerAction(type, grid, endGrid, data)`. Естественный рефлекс — сделать
так же.

Это сломает запрос. В `client_scripts.txt:307959–307965` клиент передаёт
`dTimedProductionVO` НАПРЯМУЮ третьим аргументом `SendMessagetoServer`,
без всякого `dServerAction`.

Проверка: тест из этапа 3, пункт «в теле запроса НЕТ dServerAction» (AC-2).

---

## P-3. Здания-производители описаны в `icons.xml`, а НЕ в `globals.xml`

Атрибут `productionType` в `globals.xml` встречается **0 раз**.
В `icons.xml` — **68 раз**, все на теге `<Building>`.

Источник в клиенте: `client_scripts.txt:83407`
`_local_12.productionType = _arg_5.GetAttributeInt("productionType", -1);`

Признак производителя: `productionType >= 0`. Значение `-1` — дефолт,
означает «не производитель». Не путать с `0` — это валидный тип (Barracks).

---

## P-4. `uiType` в `globals.xml` — ложный след

На `<Building>` в `globals.xml` есть атрибут `uiType` (96 вхождений). Выглядит
как то, через что можно найти бафовые здания.

Фактические значения: `CL1`..`CL5`, `DEF_MODE_L1`..`DEF_MODE_L3`. Это классы
обороны/уровня, к производству отношения не имеют.

Нужен атрибут `ui` из `icons.xml` (`timedproduction` — 47, `culture` — 20,
`warehouse` — 1). И даже он — вторичен; канонический признак — `productionType`.

## P-5. Очередь НЕ принадлежит зданию

Самая дорогая ловушка в этой фиче. У `cBuilding` есть поле
`public var productionQueue:cTimedProductionQueue;` (`client_scripts.txt:78169`) —
выглядит как собственная очередь здания.

Это **ссылка на общий объект**. `client_scripts.txt:78279–78285`:

```actionscript
if (_local_5.productionType >= 0)
{
    _local_5.productionQueue = _arg_4.mCurrentPlayerZone.GetProductionQueue(_local_5.productionType);
    if (_local_5.productionQueue == null)
    {
        _local_5.productionQueue = new cTimedProductionQueue(_arg_4, _local_5.productionType, _local_5, ...);
    };
}
```

Здание СНАЧАЛА ищет уже существующую очередь своего типа в зоне и только
если не нашло — создаёт новую (которая тут же регистрируется в зоне,
`client_scripts.txt:483888`).

Следствие: два `ProvisionHouse` в одной зоне делят одну очередь.
Игра предупреждает об этом сама: локализационный ключ
`"DuplicatedBuildingTimedProductionTip"` (`client_scripts.txt:307464`).

Если смоделировать очередь по grid — система будет думать, что свободных
слотов вдвое больше, и будет МОЛЧА терять заказы.

См. ADR-2, INV-5, FR-11.

## P-6. Очередь производства ≠ очередь строительства

В проекте есть готовая логика слотов в `build-mine`, и соблазн переиспользовать
её велик.

| | Строительство | Производство |
| --- | --- | --- |
| Класс | `cBuildQueue` (283323) | `cTimedProductionQueue` (483870) |
| Владелец | `cPlayerData.mBuildQueue`, один на игрока | `cZone.productionQueue_vector` |
| Слоты | `mMaxCount = 3` + permanent + temp | длина `mTimedProductions_vector` |
| Команды | 115 / 116 / 117 | 1025–1030 |

Запрещено читать `mBuildQueue` в этой фиче. См. ADR-1.

## P-7. Списки `<TimedProductionList id="0..4">` ПУСТЫЕ

В `globals.xml` списки с `id` = 0, 1, 2, 3, 4, 6, 7, 8, 11 содержат только
XML-комментарии и ни одного `<TimedProduction>`.

Критично: `id=1` — это `TIMED_PRODUCTION_TYPE.BUFF`, главный тип для этой фичи.
Пустой список НЕ означает «рецептов нет». Он означает, что для этого типа
работает второй механизм — динамический пул
`cBuff.GetProduceableBuffDefinitions()` с фильтрацией по `group`
(`client_scripts.txt:307936–307957`).

Если импортер будет смотреть только на `<TimedProductionList>` — получит пустой
каталог для бафов и фича не заработает вообще. См. `data-sources.md` §6.

---

## P-8. 51 рецепт из 299 НЕ имеет `<Costs>`

Статистика: `<Buff produceable="true">` — 299, из них с `<Costs>` — 248.

Неверно вывести в UI «Стоимость: 0» — это ложь. Надо выводить пометку
«стоимость неизвестна» и ставить `costs_known: false`, `complete: false`
(FR-8.5).

Ловушка второго порядка: в сводке по sequence нельзя складывать известные
стоимости и молча игнорировать неизвестные — флаг `complete` обязан
схлопываться в `false` по логическому И.

---

## P-9. Поле называется `type_string`, а не `typeString`

В `dTimedProductionVO` имя свойства — `type_string` с подчёркиванием
(`client_scripts.txt:59375–59420`). PHP-линтеры и привычка толкают к камелкейсу.

Переименование сломает десериализацию на сервере игры тихо — без ошибки
клиента, просто заказ не создастся или создастся с пустым типом.

Если линтер жалуется — добавить локальное исключение, а не переименовывать поле.

---

## P-10. Не добавлять в VO лишние поля

Класс игры имеет 14 полей. Клиент заполняет только 5. Соблазн «сделать полный
VO для точности» ведёт к тому, что в тело AMF-запроса попадут 9 лишних полей
со значением `null`, чего настоящий клиент никогда не шлёт.

См. AC-3.

---

## P-11. `stacks` по умолчанию 1 в ActionScript, но НЕ в PHP

В клиенте объявлено `public var stacks:int = 1;`. В PHP нетипизированное
свойство без инициализатора будет `null`, и в AMF уедет `null` вместо `1`.

Всегда задавать `stacks` явно. Не полагаться на дефолт (как и для `amount`).

---

## P-12. Кеш снапшота внутри одного sequence

Оптимизация «запросить зону один раз на весь sequence» выглядит безобидно и
сломает второй и последующие шаги: они увидят очередь в состоянии «до
первого заказа» и переполнят её.

Кеш допустим только с обязательной инвалидацией после КАЖДОГО успешного
заказа (ADR-10).

---

## P-13. CRLF в `client_scripts.txt`

Файл 21 МБ с CRLF-переводами строк. Регексы вида `foo$` без `\r?` будут
тихо не находить совпадений. Пустой результат grep НЕ доказывает отсутствие.

Также: инструменты поиска с лимитом размера файла могут МОЛЧА пропускать
этот файл и возвращать `results: []` без предупреждения. Использовать
`rg`/`grep`/`sed` по номерам строк.

---

## P-14. Не парсить 4.3 МБ через `simplexml_load_file`

`globals.xml` — 4 399 309 символов, `<Buff>` — 2887, `<Cost>` — 5834.
Загрузка в память целиком в CI даст памятные пики. Использовать `XMLReader`
(потоковый). И ни в коем случае — регексы по XML в продакшен-коде
(в разведочных скриптах было можно, и два раза это дало ложные пустые
результаты из-за разной расстановки пробелов в атрибутах).

## P-15. Парсер зоны сейчас не видит ничего нужного

`storage/app/parse_zone.py:221` извлекает список вида
`['buildingName_string', 'buildingGrid', 'isProductionActive', ...]`. Ни
`productionType`, ни уровня здания, ни очередей там нет.
`ZoneParserService.php` содержит ровно 0 упоминаний `production` и `buff`.

Ловушка: `isProductionActive` ЗВУЧИТ релевантно. Это флаг тумблера
команды 107 (см. P-1), а не состояние очереди производства.

Этап 2 плана обязателен и не может быть пропущен.

## P-16. Не путать команды применения бафа с командами производства

| Команда | Смысл |
| --- | --- |
| 61 `APPLY_BUFF` | применить ГОТОВЫЙ баф на здание |
| 63 `APPLY_BUFF_LIST` | применить список готовых бафов |
| 136 `REMOVE_BUFF` | снять баф |
| **91 `START_TIMED_PRODUCTION`** | **СОЗДАТЬ баф — то, что нужно** |
| 141 `DELIVER_PRODUCTION` | забрать готовое (follow-up F-1) |

Существующий `apply_buff` работает с УЖЕ ИМЕЮЩИМИСЯ бафами из инвентаря
(поэтому его payload несёт `unique_id1`/`unique_id2` — идентификатор конкретного
предмета). Новый `produce_buff` бафы СОЗДАЁТ и потому идентификаторов
предметов не имеет вообще — только имя рецепта. Не копировать структуру
payload `apply_buff`.

## P-17. Генератор каталога без детерминированной сортировки

Если команда импорта выводит ключи в порядке обхода XML или в порядке хеш-таблицы,
каждый запуск даст гигантский бессмысленный git diff, и отследить реальное
изменение после патча игры будет невозможно. Сортировать всё: ключи
`producers`, ключи `recipes`, список рецептов внутри типа, строки стоимости.

Также: поле `generated_at` с текущим временем само ломает идемпотентность
проверки из DoD этапа 1. Либо вынести его в комментарий и исключить из сравнения,
либо ставить его из хеша входных файлов, а не из времени.

## P-18. Не выдумывать лимит очереди

У `cBuildQueue` есть `mMaxCount = 3` и `IsFull()`. У `cTimedProductionQueue`
аналога НЕ НАЙДЕНО. Соблазн взять цифру «по аналогии» или из личного
игрового опыта — недопустим.

См. OQ-2: до выяснения лимита политика НЕ выставляет `QueueFull`,
a UI показывает число заказов без знаменателя.

## P-19. Отсутствующие значения `productionType`

В `icons.xml` есть 68 значений в диапазоне 0..71, но ЗНАЧЕНИЯ 3, 9, 10, 57
ОТСУТСТВУЮТ. Не считать диапазон плотным. Не делать массив фиксированной
длины и не итерировать `for ($i = 0; $i <= 71; $i++)`.

Отдельно: `TIMED_PRODUCTION_TYPE` содержит служебные константы `TYPE_HARDCODED = 10000`,
`TYPE_CULTUREBUILDING = 20000`, `TYPE_SIMPLEPRODUCTION = 30000`,
`TYPE_TIMEDPRODUCTION = 40000`. Это НЕ значения `productionType` зданий,
а маркеры категории. Не класть их в payload.

## P-20. «Универсальной мастерской» в игровых данных нет

Оператор указал ориентир «по типу как в универсальной мастерской, переплетчик».
Греп по `globals.xml`: подстрока `Universal` — 0 совпадений, `Guildhouse` — 0.

Переплётчик есть: `Bookbinder` (`productionType=2`), `AdventureBookbinder` (24).
Под «универсальной мастерской», вероятнее всего, имелся в виду
`ProvisionHouse` / `ProvisionHouse2` (Дом снабжения, `productionType` 1 и 5).

Не искать здания по русским/английским народным названиям — только по
`productionType`. Названия для отображения берутся из локализации (follow-up F-5),
а не из догадок.

## P-21. Не разворачивать `amount` в N шагов на фронте

В `Tasks.vue` уже есть готовые ветки, где мультивыбор разворачивается в N шагов
(`collect_building`, `build_mine`). Копирование этого паттерна для
`produce_buff` даст 8 шагов вместо 2 и 8 сетевых вызовов вместо 2.

Разворачивать надо только по РЕЦЕПТАМ, не по количеству. См. ADR-3-R, AC-4,
DoD этапа 7.

## P-22. Три поля VO — `double`, а не `int`

В реальном трафике команды 91 три поля закодированы маркером `0x05` (AMF3 double):

```
modifiedProductionMultiplier            = 1.0
modifiedInstantFinishCostMultiplier     = 1.0
collectedTime                           = 0.0
```

В PHP-VO они обязаны быть `float`, инициализированы `1.0` / `1.0` / `0.0`.
Если объявить `int`, кодировщик выдаст маркер целого и байт-в-байт тест
упадёт — а на живом сервере получите отказ без внятной причины.

Остальные числовые поля (`amount`, `stacks`, `index`, `productionType`,
`playerId`, `producedItems`, `buildingGrid`, `modifiedProductionAdder`,
`modifiedInstantFinishCostAdder`) — целые.

## P-23. `ArrayCollection` в AMF3 — externalizable

`flex.messaging.io.ArrayCollection` объявляет traits с флагом externalizable.
После traits идёт ОДНО вложенное значение — сам массив. Декодер, который
этого не знает, не падает, а тихо продолжает читать поток не с того места,
сдвигая ВСЕ последующие поля.

Именно на этом мой первый декодер выдал неверный результат: поля
`dGameTickCommandVO` уехали, а заказ производства «нашёлся» не там, где лежит.

**Проверка:** заказ команды 91 лежит по пути `body.data.data.data[0]`.
Если ваш парсер видит его по другому пути — он читает поток неверно.

**Действие на этапе 0:** проверить `app/Services/ZoneParserService.php` и
`storage/app/parse_zone.py` на обработку externalizable. Если её нет — это
существующий баг проекта, не связанный с этой фичей; занести в `foundbugs.md`.

## P-24. `buildingGrid` в снапшоте равен 0

В живом снапшоте у заказа `Tome` (создан Переплётчиком на гриде 8998) поле
`buildingGrid` равно **0**.

Сервер не хранит привязку заказа к зданию — только к `productionType`.
`buildingGrid` — это параметр ВЫЗОВА команды 91, а не часть состояния.

**Следствие:** нельзя показать «в этом здании 3 заказа». Можно показать только
«в очереди типа N занято 3 слота». Любая попытка отфильтровать заказы по гриду
вернёт пустоту или, что хуже, тихо неверный результат.

## P-25. `index` начинается не с нуля

При единственном заказе в очереди `index = 1`. При отправке команды 91 клиент
ставит `index = 0`, и сервер присваивает своё значение.

Не использовать `index` для подсчёта занятости — только `count(orders)`.
Не полагаться на `index` для сортировки без проверки на реальных данных.

## P-26. Индекс в `timedProductions_vector` — НЕ `productionType`

Самая дорогая ловушка снапшота. В дампе очередь с `productionType = 2` лежит
под индексом **3**. Всего 12 коллекций при 11 зданиях-производителях в зоне,
и одна коллекция ни одному зданию не соответствует.

У ПУСТОЙ коллекции нет ни `productionType`, ни любых других метаданных —
это просто пустой массив. Определить её тип невозможно в принципе.

**Запрещено:**

```php
$queue = $collections[$productionType];   // НЕВЕРНО
```

**Обязательно:** поиск по `orders[0]['productionType']`, ненайденное
трактуется как пустая очередь. См. `design.md` §4.3.

## P-27. Код ответа не равен коду запроса

Запрос `GET_ZONE = 1001` возвращает ответ с `type = 1002`. У команды 91
коды совпали случайно, и это породило ложное правило.

Не проверять успешность как `response.type === sentCommand`. Успех
определяется только `body.data.errorCode === 0`.

Наблюдённые пары из дампа: 1001 → 1002, а также ответы 1014, 1062, 1063,
4014, 1005, 15000 без известных кодов запроса (P-28).

## P-28. Как снимать дампы трафика, чтобы они были пригодны

Chrome «Copy as fetch» отдаёт тело запроса как JS-строку. AMF — бинарный
формат, и все байты, не образующие валидный UTF-8, заменяются на `U+FFFD`.
В дампе `req.txt` потеряно 5–13 байт на каждый запрос, и пострадали именно
числа — коды команд и `zoneID` восстановить невозможно.

Снимать только в base64 через перехватчик в консоли — готовый сниппет лежит
в `references/README.md`. Тогда и запрос, и ответ сохраняются без потерь.

Ответы в `req.txt` при этом целы, потому что DevTools отдаёт их отдельно и
уже в base64.
