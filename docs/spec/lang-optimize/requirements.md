# Requirements: локализация и игровые переводы

## 1. Контекст

Проект использует несколько несовместимых способов формирования пользовательских текстов:

- `LangController` публикует переводы через `/api/lang/res` и `/api/public/market/lang/res`;
- `LangParserService` во время выполнения читает внешний файл `../lang.txt` и выбирает только секции `RES`, `SPE` и `LAB`;
- `MarketSyncService` напрямую зависит от `LangParserService` и сохраняет локализованные названия игровых объектов в БД;
- `Tasks.vue`, `AccountDetail.vue` и `PublicMarketAnalytics.vue` самостоятельно загружают словарь и реализуют различающиеся fallback/normalization-алгоритмы;
- пользовательские строки захардкожены на русском, английском либо одновременно на двух языках;
- стандартные Laravel-переводы (`lang/<locale>/*.php`, `__()`, `Lang`) фактически не используются;
- в `config/app.php` уже указаны целевые `locale = en` и `fallback_locale = en`, но фактические пользовательские строки и форматирование не следуют этой конфигурации;
- HTML-документы имеют разные значения атрибута `lang` (`ru` и `en`).

Это приводит к непредсказуемым fallback-значениям, дублированию логики, зависимости runtime от внешнего XML-файла и не позволяет гарантировать английский интерфейс по умолчанию с дополнительной русской локалью.

### 1.1. Проверенные входные файлы

Спецификация уточнена после анализа предоставленных файлов:

| Параметр | `ru_lang.xml` | `en_lang.xml` |
|---|---:|---:|
| XML locale | `ru_ru` | `en_uk` |
| Размер | 8 023 145 байт | 5 368 920 байт |
| Секций | 40 | 40 |
| Записей | 36 008 | 37 242 |
| Пустых ID / текстов | 0 / 0 | 0 / 0 |
| Дубликатов | 0 | 0 |
| ID с точкой | 45 | 45 |
| ID с пробелом | 27 | 26 |
| Максимальная длина ID | 120 | 120 |
| Максимальная длина текста | 3 556 | 3 305 |

Оба файла являются валидным XML с корнем `oasis`, блоком `translations` и 40 одинаковыми именами секций. Общих ключей `(section, id)` — 36 005. Только в русском файле присутствуют 3 ключа, только в английском — 1 237 ключей. Следовательно, локали нельзя считать взаимно полными или синхронными.

SHA-256 проанализированных версий:

```text
ru_lang.xml  bbc5024370fe0dcb957c602b178b9afd5549957a0d7b3115324e84f4d8d78656
en_lang.xml  9a1c84f781faa1e5555717a665658bd2f86269167370df8cbc7a9a574df33a7d
```

Выявленные особенности формата:

- ID могут содержать точки, пробелы и `/`, поэтому их запрещено преобразовывать в Laravel dot-keys;
- основной синтаксис шаблонов: `{0}`, `{1}` и типизированные ссылки `{1,RES}`, `{1,BUI}`, `{0,ADN}`;
- встречаются фигурные скобки, которые не являются параметрами, например `{Christmas}`; импортёр не должен интерпретировать содержимое текста;
- английский каталог новее/полнее русского, особенно в `RES`, `BUI`, `LAB`, `DES` и quest-секциях;
- `ru_lang.xml` содержит 3 отсутствующих в английском ключа, включая `Loottable_CombatLoot_MysteryBox` и `Welcometext TSO Forums`.
## 2. Проблема

Необходимо создать единый, проверяемый и расширяемый механизм локализации на основе Laravel Translator. Игровые XML должны импортироваться заранее, а не парситься при HTTP-запросах или фоновых задачах. Английский должен быть основным и fallback-языком приложения, русский — дополнительной локалью. Потребители переводов не должны зависеть от выбранного языка.
## 3. Цели

- Сделать стандартные каталоги Laravel `lang/<locale>` единственным источником переводов приложения.
- Импортировать все пригодные записи английского и русского игровых XML, включая ресурсы, специалистов, баффы, задания, здания и другие игровые секции.
- Удалить runtime-зависимость от `LangController`, translation API и внешних XML.
- Унифицировать доступ к игровым переводам на backend и frontend.
- Сделать английские пользовательские тексты полными и используемыми по умолчанию.
- Сохранить русские пользовательские переводы как дополнительную локаль.
- Сохранить стабильные игровые идентификаторы и корректные fallback-значения.
## 4. Не входит в первую итерацию

- Автоматический перевод отсутствующих русских строк.
- Сложная локализация маршрутов и SEO по языкам.
- Автоматический машинный перевод.
- Изменение игрового протокола и игровых идентификаторов.
- Локализация внутренних имён классов, переменных, технических логов и комментариев.
- Рефакторинг экранов, не связанный с локализацией.
- Получение `lang.txt` из сети во время работы приложения.
## 5. Термины

- **UI-переводы** — собственные пользовательские тексты приложения: кнопки, заголовки, уведомления, ошибки, состояния.
- **Игровые переводы** — названия и шаблоны из `lang.txt`, адресуемые игровыми ID.
- **Исходный ID** — значение атрибута `id` в `lang.txt`; оно не переводится и не изменяется.
- **Секция** — значение `s[name]` в структуре `lang.txt`, например `RES`, `SPE`, `LAB`.
- **Generated-файл** — файл, созданный import-командой; вручную не редактируется.
## 6. Источники истины

1. Ручные переводы приложения: `lang/ru/*.php`.
2. Импортированные игровые переводы: `lang/ru/game.php`.
3. Frontend bundle: генерируемое представление Laravel-переводов; не редактируется вручную.
4. `lang.txt`: входной артефакт import-команды, но не runtime-зависимость.
5. Игровой ID: каноническое значение для хранения, API и поиска.

Если локализованное название хранится в БД, оно не считается каноническим и не должно использоваться как ключ поиска или идентификатор.
## 8. Функциональные требования

### FR-1. Конфигурация локали

- `config/app.php` читает локаль из `APP_LOCALE`, значение по умолчанию — `en`.
- `fallback_locale` читает `APP_FALLBACK_LOCALE`, значение по умолчанию — `en`.
- Русский язык подключается как дополнительная locale `ru`, но не становится fallback для английского интерфейса.
- HTML-атрибут `lang` формируется из текущей локали, а не захардкожен.
- Форматирование дат и времени использует текущую локаль, а не прямые `ru-RU`/`en-US` в компонентах.

### FR-2. Импорт `lang.txt`

Должна быть добавлена Artisan-команда:

```bash
php artisan tso:lang:import /path/to/ru_lang.xml --locale=ru
php artisan tso:lang:import /path/to/en_lang.xml --locale=en
```

Команда должна:

1. принять путь к входному файлу и locale;
2. прочитать `translations[language]`, нормализовать `ru_ru → ru` и `en_uk → en` и отклонить несовпадение с `--locale`;
3. проверить существование и читаемость файла;
4. безопасно разобрать XML без сетевого доступа и внешних сущностей;
5. найти все блоки переводов и все секции `s[name]`;
6. импортировать каждую запись `t[id][text]` с непустым ID;
7. сохранить точный исходный ID;
8. корректно экранировать строки в генерируемом PHP-файле;
9. записать результат детерминированно: одинаковый input создаёт побайтно одинаковый output;
10. выполнять атомарную запись через временный файл и rename;
11. вывести статистику: секции, импортированные записи, пропуски, дубликаты и ошибки;
12. завершиться с ненулевым exit code при невозможности безопасно сформировать результат;
13. поддерживать файлы текущего размера потоковым или сопоставимым по памяти способом; нельзя строить несколько полных копий XML DOM без необходимости.

Runtime приложения не должен автоматически перезаписывать `lang/ru/game.php` или `lang/en/game.php`.

### FR-3. Правила конфликтов

- Пустой ID — ошибка записи и пропуск с диагностикой.
- Пустой `text` сохраняется только при явно утверждённой политике; по умолчанию считается пропуском и попадает в отчёт.
- Повтор `(section, id)` с одинаковым текстом дедуплицируется и отражается в статистике.
- Повтор `(section, id)` с ра��ным текстом является ошибкой импорта; команда не заменяет существующий generated-файл.
- Одинаковый ID в разных секциях допустим.
- Неизвестная секция импортируется; allow-list `RES/SPE/LAB` запрещён.

### FR-4. Backend-доступ к игровым переводам

Должен существовать один типизированный application-сервис/компонент разрешения игровых названий, использующий Laravel Translator, например:

```php
$translator->get($section, $id, $fallback);
```

Требования к нему:

- lookup выполняется по точному `(section, id)`;
- возвращаемое значение всегда строка;
- для locale `en` fallback-цепочка игровых данных: `en → исходный ID`; английский интерфейс не должен неожиданно смешиваться с русским из-за 3 отсутствующих ключей;
- для locale `ru` fallback-цепочка игровых данных: `ru → en → исходный ID`, поскольку в английском файле есть 1 237 отсутствующих русских ключей;
- компонент не читает XML и не содержит статический runtime-cache;
- неизвестная секция/ID не вызывает 500;
- интерполяция выполняется только для строгих placeholders `\{<index>\}` и `\{<index>,<SECTION>\}`;
- произвольные конструкции вроде `{Christmas}` и HTML/текст в фигурных скобках сохраняются без изменения;
- типизированный placeholder, например `{1,RES}`, может рекурсивно разрешить значение параметра через соответствующую игровую секцию, но должен иметь защиту от циклов и ограничение глубины.

`MarketSyncService` и другие backend-потребители не должны зависеть от `LangParserService`.

### FR-5. Frontend-доступ

- Frontend получает переводы из статического generated bundle, создаваемого до `npm run build` либо отдельной Artisan-командой экспорта.
- Во время загрузки страниц запросы `/api/lang/res` и `/api/public/market/lang/res` не выполняются.
- Все Vue-компоненты используют единый composable/module, например `t(key, params)` и `game(section, id, params)`.
- Нормализация через перебор `Object.keys()`, удаление пробелов/underscore и сравнение lowercase не используется как основной способ lookup.
- Если backend передал игровой ID и секцию, frontend выполняет точный lookup.
- Если секция неизвестна в текущем API, используется централизованный compatibility map; локальные карты в отдельных компонентах запрещены.
- Отсутствующий ключ возвращает предсказуемый fallback и в development-режиме может один раз логироваться.

Экспортированный JSON является generated-файлом. Его источник — `lang/ru`, а не отдельный вручную поддерживаемый перевод.

### FR-6. Пользовательские строки

- Все пользовательские строки в Vue, Blade, API-ошибках и уведомлениях выносятся в именованные translation keys.
- Первая итерация содержит полные английские значения для всех пользовательских ключей.
- Русские значения хранятся в `lang/ru` и используются только при выбранной locale `ru`.
- Один элемент интерфейса не должен одновременно показывать английский и русский текст, например `Basic Resources (Базовые)`.
- Имена translation keys пишутся на английском и описывают смысл, например `ui.tasks.execute`.
- Технические сообщения логов могут оставаться на английском.
- API предпочтительно возвращает стабильный machine-readable error code; отображаемый текст локализуется единообразно.

### FR-7. Игровые сущности и БД

- Ресурсы, специалисты, баффы и другие игровые сущности идентифицируются исходными ID.
- Новая логика не должна принимать локализованное название за идентификатор.
- Market Analytics должен локализовать объект по `item_id`/`target_item_id`, а не считать сохранённые `item_name` каноническими.
- Для совместимости существующие `item_name` могут временно сохраняться, но API/UI должны иметь возможность получить актуальный перевод по ID.
- До включения переключения locale необходимо исключить зависимость исторических записей от языка, активного во время Market Sync.

### FR-8. Удаление legacy-механизма

После миграции потребителей должны быть удалены:

- `LangController`;
- маршруты `/api/lang/res` и `/api/public/market/lang/res`;
- `LangParserService`;
- runtime-чтение `base_path('../lang.txt')`;
- локальные translation/fallback-алгоритмы, заменённые общим модулем.

Удаление выполняется только после прохождения regression-тестов всех потребителей.
## 9. Нефункциональные требования

### NFR-1. Безопасность

- XML-парсер не загружает внешние сущности и сетевые ресурсы.
- Путь к input используется только CLI-командой и не принимается из публичного HTTP API.
- Generated PHP должен быть валидным PHP и не допускать выполнения содержимого `lang.txt` как кода.

### NFR-2. Производительность

- `lang.txt` не читается и не парсится в HTTP-запросах, queue jobs или scheduler.
- Production может использовать стандартные `config:cache`, `route:cache` и OPcache.
- Frontend bundle не должен загружаться отдельным запросом на каждом экране.

### NFR-3. Детерминированность

- Секции и ключи сортируются по утверждённому стабильному правилу.
- Повторный импорт без изменения input не создаёт Git diff.
- Используемая кодировка — UTF-8 без BOM.

### NFR-4. Поддерживаемость

- Один источник правды для каждого перевода.
- Новый UI-текст нельзя добавлять напрямую в шаблон без translation key.
- Новый игровой lookup не должен реализовывать собственную нормализацию.
- Generated-файлы имеют заголовок `DO NOT EDIT` и инструкцию воспроизведения.

### NFR-5. Совместимость

- PHP 8.1 и Laravel 10.
- Существующие игровые ID, API payload IDs и сохранённые записи не переименовываются.
- Миграция переводов не изменяет игровой протокол.
## 10. Инварианты

- **INV-1:** Один игровой ID никогда не заменяется локализованным текстом в доменной логике.
- **INV-2:** Runtime не зависит от наличия `lang.txt`.
- **INV-3:** Все игровые переводы доступны через единый resolver с точным lookup.
- **INV-4:** Все frontend-переводы происходят из Laravel lang source.
- **INV-5:** Неизвестный ключ не вызывает ошибку приложения и возвращает согласованный fallback.
- **INV-6:** Ошибочный импорт не повреждает последний валидный generated-файл.
- **INV-7:** Переключение между `en` и `ru` не требует изменения компонентов-потребителей.
## 11. Сценарии

### S-1. Успешный импорт

```gherkin
Given существуют валидные en_lang.xml и ru_lang.xml
When выполняется tso:lang:import для locale en и ru
Then создаются валидные lang/en/game.php и lang/ru/game.php
And импортируются все секции и записи с непустыми ID
And команда выводит статистику
And повторный импорт не создаёт diff
```

### S-2. Дублирующий конфликт

```gherkin
Given в одной секции один ID встречается с разными текстами
When выполняется импорт
Then команда завершается с ошибкой
And существующий game.php не изменяется
And конфликтующий ID указан в диагностике
```

### S-3. Отсутствующий перевод

```gherkin
Given приложение запрашивает неизвестный игровой ID
When resolver выполняет lookup
Then возвращается исходный ID или явно переданный fallback
And запрос не завершается ошибкой 500
```

### S-4. Отображение ресурса во frontend

```gherkin
Given API возвращает section RES и item_id BronzeOre
And locale по умолчанию равна en
When Vue-компонент отображает ресурс
Then показывается английское название Copper Ore
And HTTP-запрос к translation endpoint не выполняется
```

### S-5. Market Sync без lang.txt

```gherkin
Given game.php создан на этапе deployment
And внешний lang.txt отсутствует
When выполняется Market Sync
Then синхронизация завершается без ошибки локализации
And названия разрешаются через Laravel Translator
```

### S-6. Дополнительная русская локаль

```gherkin
Given locale переключена с en на ru
When открывается существующий экран
Then компонент использует русский bundle
And при отсутствии русского игрового ключа использует английский fallback
And код компонента и игровые ID не изменяются
```
## 12. Критерии приёмки

- **AC-1:** В production-коде отсутствует runtime-парсинг `lang.txt`.
- **AC-2:** В проекте отсутствуют маршруты `/api/lang/res` и `/api/public/market/lang/res`.
- **AC-3:** `LangController` и `LangParserService` удалены после миграции всех потребителей.
- **AC-4:** Import-команда обрабатывает все секции, а не только `RES/SPE/LAB`.
- **AC-5:** Повторный импорт одного input создаёт идентичный `game.php`.
- **AC-6:** Конфликтующие дубликаты не перезаписывают валидный output.
- **AC-7:** Tasks, Account Detail, Market Analytics и Public Market Analytics отобража��т игровые названия через общий механизм.
- **AC-8:** `MarketSyncService` не зависит от XML parser.
- **AC-9:** На основных экранах нет смешанных русско-английских пользовательских строк.
- **AC-10:** `APP_LOCALE=en` и `APP_FALLBACK_LOCALE=en` являются рабочей конфигурацией по умолчанию; `ru` доступен как дополнительная locale.
- **AC-11:** Отсутствующий игровой перевод отображает согласованный fallback.
- **AC-12:** `php artisan test`, Pint, PHPStan и `npm run build` завершаются успешно.
- **AC-13:** Переключение с основной `en` на дополнительную `ru` не требует изменения Vue-компонентов или backend-потребителей.
