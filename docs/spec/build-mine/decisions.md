# Decisions (ADR): build_mine / upgrade_mine

Отклонение от любого ADR без правки этого файла запрещено.

## ADR-1. Два типа задачи, а не один с флагом режима

**Контекст.** Постройка и апгрейд — разные команды (`50` и `60`), разные предпосылки,
разные формы пакета и разные последствия ошибки.

**Альтернативы.**
1. Один тип `mine_action` с `payload.action = build|upgrade`.
2. Два независимых типа задачи.

**Решение.** Два типа: `build_mine` и `upgrade_mine`.

**Обоснование.** В `collect_building` один тип с режимами оправдан тем, что для игрока это
одно понятие («щёлкнуть по зданию»). Здесь понятия разные: «поставить новую шахту» и
«улучшить существующую» — разные предпосылки (грид должен быть пуст против грид должен
быть занят шахтой), поэтому объединение потребовало бы ветвления по флагу в каждой
проверке. Это прямое нарушение SRP и источник ошибок вида «применил проверку не того
сценария».

**Цена.** Два хендлера вместо одного. Компенсируется общей инфраструктурой (каталог,
снапшот, бюджет очереди), которая переиспользуется без копирования.

## ADR-2. Решение о допустимости — в отдельном чистом объекте политики

**Решение.** `MinePlacementPolicy` и `MineUpgradePolicy` возвращают неизменяемые
`PlacementDecision` / `UpgradeDecision`. Политики не имеют доступа ни к сети, ни к БД,
ни к фасадам Laravel.

**Обоснование.** Это самая ответственная логика фичи: она решает, будут ли потрачены
ресурсы игрока. В виде чистой функции она покрывается таблицей unit-тестов за секунды.
Внутри хендлера тот же набор случаев требовал бы feature-тестов с моками транспорта.
Прецедент в проекте: `BuildingClickResolver` + `BuildingClickDecision`.

## ADR-3. Причина отказа — enum, а не строка

**Решение.** `PlacementRejectionReason` и `UpgradeRejectionReason` — строковые enum.

**Обоснование.** Причина используется в трёх местах: лог, строка результата задачи и поле
`reason` в API для UI. Строковые литералы в трёх местах разъезжаются. Enum даёт
исчерпывающий `match` и гарантию, что для каждой причины есть ключ локализации.

## ADR-4. Номера зданий — в `config/game.php`, а не в константах кода

**Решение.** Каталог шахт живёт в конфиге, класс `ConfigMineCatalog` его читает.

**Обоснование.** Номера — внешние игровые данные, которые могут измениться при обновлении
клиента игры. Правка при этом должна быть однострочной и не требовать пересборки логики.
Прецедент: `config/game.php` → `collectibles.clickable_patterns`.

**Дополнительно.** Каталог одновременно служит allow-list: это осознанное совмещение,
потому что «знаю номер» и «разрешено строить» здесь — одно и то же множество из шести
записей. Не-шахты в каталог не попадают, поэтому апгрейд не-шахты невозможен даже при
явном указании грида.

## ADR-5. Источник истины — только свежий снапшот зоны

**Решение.** Обработчики всегда запрашивают зону заново и никогда не используют
кэш `Account::$zone_data`.

**Обоснование.** Грид — это координата, а не идентификатор объекта. Между планированием
задачи и её исполнением на гриде могло появиться здание, а залежь могла истощиться.
Постройка по устаревшим данным — трата ресурсов и занятый слот очереди.

**Цена.** Один дополнительный игровой запрос на шаг. Принято осознанно; тот же компромисс
уже принят в `collect_building` (ADR-10 той спеки).

## ADR-6. Один грид на задачу; массовость — через `sequence`, а не батч внутри хендлера

**Контекст.** Юзерскрипт отправляет пачку команд в одном проходе, ограничивая её
свободными слотами очереди и интервалом 1000 мс.

**Решение.** Хендлер обрабатывает ровно один грид. Мультивыбор в UI разворачивается в N
шагов `sequence` с `delay_seconds >= 1`.

**Обоснование.** Движок последовательностей проекта уже умеет ровно то, что нужно:
задержки между шагами, частичный успех, повтор отдельного шага,
`StepResultCollection`. Батч внутри хендлера продублировал бы эту логику и сломал бы
принцип «одно действие = один предсказуемый результат». Прецедент: `collect_building`,
ADR-9.

**Следствие.** Требование FR-9 о троттлинге реализуется задержкой шага, а не sleep внутри
хендлера. Sleep внутри хендлера запрещён: он блокирует воркер очереди.

## ADR-7. Отсутствие данных об очереди стройки = запрет действия

**Решение.** Если снапшот не содержит очередь стройки, `BuildQueueBudget` сообщает о нуле
свободных слотов и политика отказывает.

**Альтернатива (отвергнута).** Считать неизвестную очередь свободной и «пусть сервер решит».

**Обоснование.** Fail-safe. Пропуск действия обратим (задача выполнится в следующий раз),
а отправка команды при полной очереди в лучшем случае бесполезна, в худшем — занимает
слот непредсказуемым образом. Дополнительно это защищает от ситуации, когда доработка
парсера ещё не задеплоена, а код уже обновлён: тогда фича безопасно ничего не делает.

## ADR-8. Критерий «можно строить» — пустой грид, а не флаг `accessible`

**Контекст.** У `dDepositVO` есть поле `accessible` (`DEPOSIT_ACCESSIBLE_TYPES`), которое
выглядит как очевидный признак «залежь разведана».

**Решение.** Основной критерий — залежь присутствует в снапшоте, остаток больше нуля и на
гриде нет никакого здания. Поле `accessible` применяется только как дополнительный
фильтр, если оно присутствует в данных.

**Обоснование.** Рабочий юзерскрипт (`user_drunken_miner.js:916–929`) не проверяет
`accessible` вообще: неразведанные залежи не попадают в контейнер залежей. Строгая
проверка `accessible` на непроверенном перечислении рискует отказать по всем залежам —
то есть тихо сломать фичу. Мягкий фильтр даёт то же поведение, что у проверенного
источника.

**Следствие.** `parse_zone.py` всё равно извлекает `accessible` — чтобы поле было доступно
для диагностики и последующего усиления политики.

## ADR-9. Отдельный адаптер-шлюз вместо прямой зависимости хендлера от `TsoAmfService`

**Решение.** Хендлеры зависят от `MineCommandGatewayInterface` с двумя методами;
`AmfMineCommandGateway` реализует его через `TsoAmfService`.

**Альтернатива (отвергнута).** Инжектировать `TsoAmfService` напрямую, как в
`StopProductionHandler`.

**Обоснование.** ISP и тестируемость: `TsoAmfService` — крупный класс с сетью, сессиями и
релогином. Узкий интерфейс из двух методов подменяется в тестах тривиальным фейком, и
хендлер тестируется без HTTP. Дополнительно это фиксирует границу: единственный код,
имеющий право отправить команды `50` и `60`, — один класс-адаптер.

**Цена.** Один лишний интерфейс и класс. Оправдано тем, что речь о необратимых игровых
действиях.

## ADR-10. Типизированный снапшот зоны вместо сырых массивов

**Решение.** Ввести `ZoneSnapshot`, `DepositSnapshot`, `BuildingSnapshot`,
`BuildQueueSnapshot` как `final readonly` объекты; разбор сырого массива —
в единственном месте (`AmfZoneSnapshotProvider`).

**Обоснование.** Существующий код обращается к зоне выражениями вида
`(int) ($b['buildingGrid'] ?? $b['grid'] ?? 0)`, повторёнными в нескольких файлах. Для
фичи с необратимыми последствиями такие обращения — источник тихих ошибок (опечатка в
ключе даёт `0` и «пустой грид»). Один разбор + типы, которые проверяет phpstan.

**Границы.** Существующие потребители зоны не переписываются (INV-5). Новые типы
используются только новым кодом.

## ADR-11. Апгрейд ограничен шахтами из каталога

**Контекст.** Команда `60` универсальна и улучшает любое здание.

**Решение.** `upgrade_mine` отказывает, если здание на гриде не входит в каталог шахт.

**Обоснование.** Иначе один тип задачи стал бы универсальным «улучшить что угодно» с
непроверенной семантикой для сотен зданий. Универсальный апгрейд — отдельная задача с
отдельной проверкой. Название типа задачи должно честно описывать его полномочия.

## ADR-12. Отказ политики — успешный исход задачи, а не ошибка

**Решение.** Запрет политики возвращает локализованную строку результата; исключения
бросаются только при `grid <= 0`, ошибке зоны и сессионных кодах.

**Обоснование.** Планировщик запускает задачи периодически. «Залежь ещё занята» или «очередь
полна» — нормальное состояние мира, а не сбой. Исключения в этих случаях замусорили бы
журнал ошибок и включили бы механизм повторов там, где повтор бессмысленен.

## ADR-13. UI отправляет `mode`-независимый payload; выбора «сырых» параметров нет

**Решение.** UI передаёт только `grid` (плюс отображаемые имена и `max_level` для апгрейда).
Номер здания в payload не передаётся никогда.

**Обоснование.** Номер — внутренний протокольный параметр. Если он попадёт в payload,
устаревшая задача из БД сможет отправить произвольный номер в обход каталога. Номер
всегда вычисляется в момент исполнения из имени руды в свежем снапшоте (INV-1).
