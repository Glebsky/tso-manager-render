# Requirements: build_mine / upgrade_mine

## Контекст и проблема

В планировщике задач уже есть остановка и запуск производства, отправка геологов и
специалистов, применение баффов и сбор коллекций. Нет ни одного типа задачи, который
создаёт или улучшает здание.

Практический сценарий игрока: геолог разведал залежь, на разведанной залежи можно
поставить шахту, шахту потом нужно улучшать до 7 уровня. Сейчас это делается только
руками в игровом клиенте.

Обе игровые команды уже объявлены в проекте и не используются:
`TsoAmfService::CMD_BUILD = 50`, `TsoAmfService::CMD_UPGRADE = 60`.

## Цели

1. Два новых типа действия: `build_mine` и `upgrade_mine`, работающие и как самостоятельная
   задача, и как шаг последовательности (`sequence`).
2. Полная валидация цели на свежем снапшоте зоны до отправки команды.
3. Невозможность построить не то здание, не на ту залежь и не на тот грид.
4. Учёт очереди стройки: не отправлять команды, которые сервер гарантированно отклонит.
5. UI, в котором игрок видит только те залежи и шахты, с которыми действие имеет смысл.
6. Нулевая регрессия для существующих типов задач.

## Функциональные требования

### FR-1. Новые типы действия

В `App\Enums\TaskType` добавляются два случая:

```php
case BuildMine = 'build_mine';
case UpgradeMine = 'upgrade_mine';
```

Оба доступны как самостоятельная задача и как шаг внутри `sequence`.
Одно действие = ровно один грид.

### FR-2. Payload `build_mine`

```json
{
  "grid": 6431,
  "deposit_name": "IronOre",
  "building_name": "IronMine",
  "name": "Железная шахта (6431)"
}
```

| Поле | Правило | Роль |
| --- | --- | --- |
| `grid` | `required|integer|min:1` | грид залежи, он же грид будущей шахты |
| `deposit_name` | `nullable|string|max:255` | подсказка для UI и логов; **решение принимается по снапшоту, а не по этому полю** |
| `building_name` | `nullable|string|max:255` | то же: отображение, не источник истины |
| `name` | `nullable|string|max:255` | человеческое имя задачи |

### FR-3. Payload `upgrade_mine`

```json
{
  "grid": 6431,
  "building_name": "IronMine",
  "max_level": 7,
  "name": "Апгрейд железной шахты (6431)"
}
```

| Поле | Правило | Роль |
| --- | --- | --- |
| `grid` | `required|integer|min:1` | грид существующей шахты |
| `max_level` | `nullable|integer|min:1|max:7` | целевой уровень; по умолчанию `7` |
| `building_name`, `name` | `nullable|string|max:255` | отображение |

### FR-4. Серверная сверка цели перед отправкой (build_mine)

Перед отправкой команды обработчик обязан:

1. загрузить **свежий** снапшот зоны (никогда не использовать кэш `zone_data`);
2. проверить `errorCode == 0`, иначе бросить `GameServerErrorException`;
3. найти залежь на `grid`; если её нет — skip;
4. определить шахту по имени руды через каталог; если руды нет в каталоге — skip;
5. проверить, что `amount > 0`; иначе skip;
6. проверить, что на `grid` **нет никакого здания**; иначе skip;
7. проверить, что в очереди стройки есть хотя бы один свободный слот; иначе skip;
8. только после этого отправить команду `50`.

### FR-5. Серверная сверка цели перед отправкой (upgrade_mine)

1. свежий снапшот зоны, проверка `errorCode`;
2. на `grid` есть здание; иначе skip;
3. имя здания входит в каталог шахт; иначе skip (апгрейдить не-шахты эта задача не имеет права);
4. текущий `upgradeLevel < min(payload.max_level, определение.maxUpgradeLevel)`; иначе skip «уже нужного уровня»;
5. апгрейд не идёт прямо сейчас (`upgradeIsInProgress` ложно); иначе skip;
6. в очереди стройки есть свободный слот; иначе skip;
7. отправить команду `60`.

### FR-6. Формы отправляемых пакетов

| Действие | `commandType` | `dServerAction` |
| --- | --- | --- |
| `build_mine` | `50` | `{type: <buildingNumber>, grid: <grid>, endGrid: 0, data: null}` |
| `upgrade_mine` | `60` | `{type: 0, grid: <grid>, endGrid: 0, data: null}` |

Внимание: для команды `50` поле `type` — это **номер здания**, а не вид действия.
Это отличается от всех существующих методов сервиса (например `stop_production`,
где `type` = `0`/`1`). Формы фиксируются snapshot-тестами.

### FR-7. Каталог шахт

Единственный источник соответствия «руда → шахта → номер здания» — `config/game.php`:

| Руда | Шахта | Номер | Макс. уровень |
| --- | --- | --- | --- |
| `BronzeOre` | `BronzeMine` | `36` | `7` |
| `Coal` | `CoalMine` | `37` | `7` |
| `GoldOre` | `GoldMine` | `46` | `7` |
| `IronOre` | `IronMine` | `50` | `7` |
| `Salpeter` | `SalpeterMine` | `63` | `7` |
| `TitaniumOre` | `TitaniumMine` | `69` | `7` |

Каталог одновременно выполняет роль allow-list: руда или здание вне каталога = отказ.

### FR-8. Очередь стройки

Снапшот зоны обязан содержать очередь стройки: сколько слотов занято и сколько всего.
Если данных нет (`null`), политика обязана считать это **отсутствием свободных слотов**
и отказывать — безопасное поведение по умолчанию.

### FR-9. Троттлинг

Между двумя игровыми командами постройки/апгрейда должно проходить не менее 1000 мс.
Массовый выбор в UI разворачивается в шаги `sequence` с `delay_seconds >= 1`.
Батч-режим внутри одной задачи не реализуется (см. ADR-6).

### FR-10. Результаты выполнения

Строки результата берутся только из `lang`, содержат имя объекта и грид,
не превышают `game.tasks.max_result_length`:

- `Шахта: построена IronMine (грид 6431)`
- `Шахта: пропуск, грид 6431 занят зданием`
- `Шахта: пропуск, нет свободных слотов очереди стройки`
- `Шахта: улучшение IronMine до уровня 4 (грид 6431)`
- `Шахта: пропуск, IronMine уже уровня 7`

### FR-11. Обработка ошибок

| Ситуация | Поведение |
| --- | --- |
| Зона вернула `errorCode != 0` | `GameServerErrorException` |
| Политика запретила действие | skip: строка результата из `lang`, **без AMF-вызова**, задача считается успешной |
| `grid <= 0` в payload | `InvalidTaskTypeException` (422) |
| Ответ игры `1005` / `1012` | пробрасывается наружу для релогина и повтора |
| Прочие игровые коды | лог `warning` + текст из `GameErrorResolver::getMessage()` |
| Ответ AMF не парсится | трактуется как успех (как в `CollectBuildingHandler::extractErrorCode`) |

### FR-12. Логирование

Префиксы `[BuildMine]` и `[UpgradeMine]`. Обязательные поля: `account_id`, `grid`,
имя руды/здания, номер здания, свободные слоты очереди, машиночитаемая причина решения
(`reason`), игровой код ответа. Решение политики логируется **всегда**, включая отказы:
это аудиторский след того, почему была или не была потрачена ресурсная база игрока.

### FR-13. Read-only эндпоинты для UI

`GET /api/game/buildable-deposits?account_id={id}` под `auth:sanctum`:

```json
{
  "data": [
    {"grid": 6431, "deposit_name": "IronOre", "building_name": "IronMine",
     "amount": 12400, "max_amount": 15000, "buildable": true, "reason": "ok"},
    {"grid": 6502, "deposit_name": "Coal", "building_name": "CoalMine",
     "amount": 0, "max_amount": 9000, "buildable": false, "reason": "deposit_empty"}
  ]
}
```

`GET /api/game/upgradable-mines?account_id={id}`:

```json
{
  "data": [
    {"grid": 6431, "building_name": "IronMine", "level": 3, "max_level": 7,
     "upgradable": true, "reason": "ok"}
  ]
}
```

Требования: только чтение, никаких игровых команд; кэш на 30 секунд по образцу
`ClickableBuildingListService`; при сбое загрузки зоны — `200` с пустым `data`,
не `500`.

### FR-14. UI в планировщике задач

В `resources/js/views/Tasks.vue`:

1. Два новых пункта в выпадающем списке действий: «Построить шахту», «Улучшить шахту».
2. Модалка выбора цели со списком из соответствующего эндпоинта: грид, руда/шахта,
   остаток ресурса или текущий уровень.
3. Мультивыбор разворачивается в `sequence` с `delay_seconds = 1` для каждого шага.
4. Недоступные строки (`buildable: false` / `upgradable: false`) показываются с причиной,
   но не выбираются.
5. Все подписи — через `lang`, никакого текста в шаблоне.

## Инварианты

- **INV-1 (безопасность).** Команда `50` отправляется только если каталог содержит руду
  найденной залежи, а грид пуст по свежему снапшоту. Значения `payload.building_name` и
  `payload.deposit_name` никогда не влияют на решение.
- **INV-2 (протокол).** Формы пакетов соответствуют FR-6 и зафиксированы тестами.
- **INV-3 (отказ по умолчанию).** Любые недостающие или неоднозначные данные снапшота
  трактуются как запрет действия.
- **INV-4 (единый резолвер).** UI-список и обработчик задачи используют одну и ту же
  политику. Невозможна ситуация «в списке доступно, а обработчик отказывает по другой логике».
- **INV-5 (регрессия).** `collect_pickups`, `collect_building`, `stop_production`,
  `start_production`, `apply_buff`, `send_specialist` и публичный контракт их payload
  не изменяются.
- **INV-6 (идемпотентность на уровне исхода).** Повторный запуск задачи после успешной
  постройки даёт skip «грид занят», а не вторую постройку.
- **INV-7 (только чтение в UI).** Эндпоинты FR-13 не отправляют игровых команд, кроме
  чтения зоны.
- **INV-8 (границы каталога).** В каталоге ровно шесть записей из FR-7. Epic/Arctic/Endless
  шахты не добавляются в рамках этой задачи.

## Критерии приёмки

- **AC-1.** Задача `build_mine` на разведанной пустой залежи `IronOre` отправляет ровно один
  вызов с `commandType = 50` и `dServerAction{type: 50, grid: <grid>, endGrid: 0, data: null}`.
- **AC-2.** Задача `upgrade_mine` на шахте 3 уровня отправляет ровно один вызов с
  `commandType = 60` и `dServerAction{type: 0, grid: <grid>, endGrid: 0, data: null}`.
- **AC-3 (безопасность).** Если на гриде уже стоит здание, AMF-вызов **не выполняется**,
  задача возвращает skip.
- **AC-4 (безопасность).** Если руда залежи отсутствует в каталоге, AMF-вызов не выполняется.
- **AC-5.** Если в очереди стройки нет свободных слотов, AMF-вызов не выполняется.
- **AC-6.** `upgrade_mine` на не-шахте (например `Woodcutter`) не выполняет AMF-вызов.
- **AC-7.** `upgrade_mine` при `upgradeLevel >= max_level` не выполняет AMF-вызов.
- **AC-8.** Коды `1005`/`1012` приводят к релогину и повтору; прочие коды — к skip с сообщением.
- **AC-9.** Валидация отклоняет payload без `grid` и с `max_level` вне `1..7`.
- **AC-10.** `parse_zone.py` на сохранённом дампе зоны возвращает непустой массив `deposits`
  с полями `grid`, `name`, `amount`, `max_amount` и объект `build_queue` с `used`/`total`.
- **AC-11.** Мультивыбор из N залежей создаёт последовательность из N шагов с задержкой
  не менее 1 секунды между шагами.
- **AC-12.** Все гейты зелёные, `phpstan-baseline.neon` не растёт.
