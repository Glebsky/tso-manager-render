# Requirements: collect_building (revision 2)

## Контекст и проблема

Сейчас есть только `collect_pickups`: он перебирает все здания зоны, фильтрует их
по шаблонам имён и шлёт `DESTRUCT_BUILDING` на каждое. Три разрыва:

1. Праздничные здания (Christmas Tree, `FlyingHouse`, воздушные шары) вообще не собираются
   командой `65`: их подарок выдаётся через квест-триггер (`QUEST_TRIGGER`, 100).
   Попытка обработать их старым путём ОПАСНА: для обычного здания `65` — снос.
2. Оператор хочет точковое действие на конкретное здание, а не массовый перебор.
3. В сериях нужен детерминированный шаг с предсказуемым результатом.

## Цели

1. Новый тип действия `collect_building`, работающий как одиночная задача и как шаг серии.
2. Поддержка двух игровых механик без утечки игрового протокола в UI и API.
3. Невозможность случайно снести здание игрока — главное требование безопасности.
4. Визуальная часть меняется минимально.
5. Нулевая регрессия для существующих типов задач.

## Функциональные требования

### FR-1. Новый тип действия

`TaskType::CollectBuilding = 'collect_building'`. Доступен как самостоятельная задача
и как шаг внутри `sequence`. На одно действие — ровно одно здание.

### FR-2. Режимы и автовыбор

Поддерживаются три значения `payload.mode`:

| `mode` | Поведение |
| --- | --- |
| `auto` (по умолчанию) | Сервер сам определяет режим по имени здания из свежей зоны |
| `collectible` | Явно ветка `DESTRUCT_BUILDING (65)`; проходит только с allow-list |
| `quest_trigger` | Явно ветка `QUEST_TRIGGER (100)` |

Правило автовыбора в `auto`: если имя здания в allow-list коллекций → `collectible`;
иначе → `quest_trigger`. Обратное направление запрещено: автовыбор НИКОГДА
не приводит к `65` без попадания в allow-list. То есть неизвестное здание всегда
уходит в безопасную ветку `100`.

### FR-3. Payload

Переиспользуется существующая форма building-задач:

```json
{
  "grid": 7215,
  "building_name": "FlyingHouse",
  "building_raw_name": "FlyingHouse",
  "mode": "auto"
}
```

Обязателен только `grid` (`integer|min:1`). `mode` — `nullable|string|in:auto,collectible,quest_trigger`.
Имена из клиента — только для читаемости и логов; решения на них не основываются.
Новый блок правил не создаётся: тип входит в `isBuildingTask()` и в building-ветку
`sequenceRules()`, плюс одно правило для `mode`.

### FR-4. Серверная сверка цели

Перед отправкой любой команды хендлер обязан:

1. загрузить свежую зону (без кеша);
2. найти здание с указанным `grid`; если не найдено — скип, команда не шлётся;
3. определить режим по FR-2;
4. для режима `collectible` — проверить имя по allow-list; не прошло → ошибка без AMF-вызова.

Сверка выполняется только по свежему состоянию зоны: `grid` — позиция на карте, и
между созданием задачи и её выполнением игрок мог поставить туда другое здание.

### FR-5. Источники знаний о целях

- **Коллекции**: шаблоны имён из `config/game.php` → `collectibles.clickable_patterns`,
  читаются `ClickableBuildingRegistry`. `parse_zone.py` не трогается (ADR-2).
- **Квестовые подарки**: авторитетный источник — игровой пул квестов
  (`QUEST_TRIGGER` с `type = 4`), из которого берутся триггеры
  `TYPE_BUILDING` + `CONDITION_SELECTED`. Список имён зданий из них и есть точный
  перечень «где сейчас есть подарок». Шаблоны имён для этой ветки не требуются.

Чтение пула квестов — опциональная возможность удобства (этап 6 плана). Его
недоступность НЕ блокирует выполнение задачи: в ветке `100` лишний клик безопасен.

### FR-6. Отправляемые команды

| Режим | commandType | `dServerAction` |
| --- | --- | --- |
| `collectible` | `65` | `{type: 0, grid: <grid>, endGrid: 0, data: "cCollectibleBuilding"}` |
| `quest_trigger` | `100` | `{type: 2, grid: 0, endGrid: 0, data: <grid>}` |

Форма пакетов воспроизводит клиент 1:1 и закрепляется snapshot-тестом.

### FR-7. Результат выполнения

Строка результата в терминах предметной области, без номеров команд и без слова
«снос», чтобы не пугать оператора и не раскрывать протокол:

- `Здание: собрано Herbs (grid 7215)`
- `Здание: подарок получен FlyingHouse (grid 7301)`
- `Здание: на сетке 7215 нечего собирать`

Ограничение длины — существующий `game.tasks.max_result_length`.

### FR-8. Обработка ошибок

| Ситуация | Поведение |
| --- | --- |
| Зона вернула `errorCode != 0` | `GameServerErrorException` |
| На `grid` нет здания | Скип, `tasks.building_collect.not_found`, задача не падает, команда не шлётся |
| `mode = collectible`, имя не в allow-list | `BuildingNotClickableException`, **ни одного AMF-вызова** |
| Коды `1005` / `1012` | Пробрасываются для релогина и retry в исполнителях |
| Код `551` (`QUEST_TRIGGER_ERROR`) | Скип с warning: сервер считает, что подарка сейчас нет |
| Прочие игровые коды | Скип с warning и понятным текстом из `GameErrorResolver` |
| Нераспарсиваемый ответ AMF | Трактуется как успех (как в `CollectPickupsHandler`) |

### FR-9. Локализация

Ключи в `lang/{en,ru,uk}/ui.php` и `lang/{en,ru,uk}/tasks.php`. Генерированные фронтенд-JSON —
только штатной командой экспорта, не руками.

### FR-10. Логирование

Префикс `[CollectBuilding]`. Обязательные поля: `account_id`, `grid`, имя здания из зоны,
выбранный режим и основание выбора, игровой код ответа. Секреты и токены не логируются.
Решение о режиме логируется всегда, даже при успехе — это единственный аудиторский след
того, почему была отправлена потенциально разрушительная команда.

## Инварианты

- **INV-1 (безопасность).** `DESTRUCT_BUILDING` отправляется только когда имя здания
  на этом `grid` в свежей зоне совпало с allow-list. Никакое значение `payload` не
  может обойти эту проверку.
- **INV-2 (протокол).** Формы обоих пакетов соответствуют FR-6 и зафиксированы тестом.
- **INV-3 (регрессия).** `collect_pickups`, `parse_zone.py`, схема БД и публичный
  контракт существующих эндпоинтов не изменяются.
- **INV-4 (UI).** Нет новых компонентов, модалок и CSS. Единственное видимое
  изменение — новый пункт в существующем дропдауне действий.
- **INV-5 (ADR-001).** Один оператор; идентификаторы из клиента недоверенные.
- **INV-6 (идемпотентность).** Повторный запуск безопасен: собранная коллекция
  исчезает из зоны (→ скип), повторный квест-триггер — no-op на сервере.

## Критерии приёмки

- **AC-1.** Оператор создаёт задачу через существующую форму и модалку выбора зданий;
  мультивыбор из N зданий даёт N действий.
- **AC-2.** Клик по коллекции: ровно один вызов команды `65` с правильным `grid`.
- **AC-3.** Клик по праздничному зданию: ровно один вызов команды `100`
  с `dServerAction{type: 2, data: grid}` и **ни одного вызова `65`**.
- **AC-4 (главный).** Задача с `mode = collectible`, нацеленная на производственное
  здание, завершается ошибкой и не делает НИ ОДНОГО AMF-вызова.
- **AC-5.** `mode = auto` на неизвестном здании выбирает `quest_trigger`, не `collectible`.
- **AC-6.** Исчезнувшая цель: задача не падает, результат объяснительный.
- **AC-7.** Коды `1005`/`1012` ведут к релогину и retry; `551` — к скипу без падения задачи.
- **AC-8.** API отклоняет payload без `grid` и с неизвестным `mode`.
- **AC-9.** Все четыре гейта зелёные, `phpstan-baseline.neon` не вырос.
