# Decisions: collect_building (revision 2)

## ADR-1. Один тип задачи с двумя режимами, а не два типа

**Контекст.** Сбор коллекции и получение подарка — разные команды (`65` и `100`)
с разной формой пакета.

**Альтернативы.**
1. Два типа задач: `collect_building` и `click_gift_building`.
2. Один тип, режим выбирает сервер (выбрано).

**Решение.** Один тип `collect_building` с `payload.mode` и значением `auto` по умолчанию.

**Обоснование.** Для оператора это одно и то же намерение: «нажать на здание и забрать,
что дадут». Различие — деталь реализации игры, которая может отличаться даже у двух
внешне одинаковых праздничных зданий. Два типа заставили бы оператора угадывать
внутреннюю механику и удвоили поверхность UI вместо одной строки в дропдауне.

**Цена.** Внутри хендлера есть ветвление. Оно локализовано в одном `match` и
опирается на готовое решение `BuildingClickDecision`, а не на разбор payload.

## ADR-2. Решение о ветке — в отдельном чистом объекте

**Решение.** `BuildingClickResolver` + иммутабельный `BuildingClickDecision`.
Хендлер оркестрирует, но не решает.

**Обоснование.** Решение «шлём ли команду сноса» — самая ответственная строка во всей
фиче. В виде чистой функции оно покрывается таблицей unit-тестов без моков, базы и
сети, что даёт исчерпывающее покрытие за секунды. Если бы логика жила в хендлере,
каждый случай требовал бы Feature-теста с тремя моками.

## ADR-3. Новый метод AMF вместо расширения `collectCollectible()`

**Контекст.** В ветке `100` `grid` едет в `data`, а `type` — это номер quest-stack, а не `0`.

**Отвергнуто.** Добавить в `collectCollectible()` флаг или необязательные параметры.

**Обоснование.** Общего у двух вызовов — только слово «grid». Флаг сделал бы метод
двусмысленным и поставил под угрозу работающий `collect_pickups`: ошибка в
значении флага молча превратила бы безобидный клик в снос. Два явных метода —
два явных контракта, каждый со своим snapshot-тестом.

## ADR-4. Allow-list обязателен только для опасной ветки

**Решение.** Жёсткий серверный allow-list — только перед `65`. Для `100` проверка
мягкая: достаточно, чтобы здание существовало на указанном `grid`.

**Обоснование.** Строгость должна быть пропорциональна цене ошибки. Цена ошибки в
`65` — безвозвратно снесённое здание; в `100` — один лишний игнорируемый пакет.
Требовать список имён для ветки `100` означало бы вечный ручной патч-лист
праздничных зданий без выигрыша в безопасности — чистый организационный долг.

## ADR-5. `auto` падает в безопасную ветку

**Решение.** Неизвестное имя в режиме `auto` → `quest_trigger`, никогда не `collectible`.

**Обоснование.** Классификатор на регулярках будет ошибаться — это вопрос когда, а не
если. Стоимость ошибки асимметрична, поэтому направление ошибки выбирается
явлюй: лучше не собрать коллекцию, чем снести ратушу.

**Побочный эффект.** Новая коллекция с нетипичным именем не соберётся, пока её
шаблон не добавят в конфиг. Это видно в логах (`reason = auto_fallback_safe`) и
лечится правкой конфига без деплоя кода.

## ADR-6. Режим не показывается в UI

**Решение.** UI всегда отправляет `mode: 'auto'`. Явные режимы — только через API.

**Обоснование.** Требование «визуал не меняется особо» + отсутствие смысла для
оператора: выбор режима — это возможность ошибиться в сторону сноса без всякой
пользы. Оставлять такой рычаг в интерфейсе — плохое проектирование безопасности.

## ADR-7. Классификация коллекций живёт в PHP-конфиге

**Решение.** `config/game.php`, а не константы в хендлере и не `parse_zone.py`.

**Обоснование.** Решение о отправке опасной команды обязано приниматься в том же
процессе, который её отправляет; доверять полю, проклассифицированному внешним
скриптом, нельзя.

**Цена.** Два списка имён (Python для `collect_pickups`, PHP для этой фичи). Расхождение
всегда даёт ложный отказ, никогда ложное разрешение. Follow-up F-1.

## ADR-8. Пул квестов — подсказка, а не шлюз

**Контекст.** Из пула квестов можно точно узнать, где сейчас есть подарок.

**Отвергнуто.** Сделать пул квестов обязательным условием выполнения.

**Обоснование.** Это добавило бы второй сетевой вызов в критический путь каждого
шага и новую точку отказа ради защиты от безвредного no-op. При этом сервер и
так является авторитетом: если подарка нет, он ответит `551`.

**Следствие.** Пул квестов используется только для подсветки зданий в существующей
модалке и ставится последним этапом плана.

## ADR-9. Один `grid` на действие

**Решение.** Мультивыбор в UI разворачивается в N действий серии, как в
`task-planner-multi-select`. Массивов grid в payload нет.

**Обоснование.** Совместимость с существующим планировщиком: частичный успех,
задержки между шагами, retry пошагово и `StepResultCollection` уже работают.

## ADR-10. Сверка только по свежей зоне

**Решение.** Кеш `zone_data` для проверки цели не используется.

**Обоснование.** `grid` — позиция на карте, а не идентити объекта. Коллекция могла
исчезнуть, а игрок — поставить туда реальное здание. Старый кеш в таком сценарии
разрешил бы снос.

**Цена.** Один дополнительный запрос зоны на шаг. Принято осознанно; оптимизация —
сквозной снимок зоны на всю серию с коротким TTL — вынесена в follow-up F-3.

## ADR-11. Без новых компонентов UI

**Решение.** Только пункт дропдауна, карты иконок/лейблов и ветка payload.

**Обоснование.** Прямое требование заказчика; плюс любой новый компонент пришлось бы
заново покрывать поведением закрытия, поиска и категорий, уже реализованным в
существующей модалке.
