# Decisions (ADR): market-tradeables

> Отступать от этих решений без обновления этого файла ЗАПРЕЩЕНО.
> Если решение кажется неверным — остановись и спроси, а не импровизируй.

## ADR-1. Читаем `dTradeObjectVO.type` и ветвимся по нему

**Контекст.** Поле уже приходит в PHP (`parse_market.py` сериализует все
атрибуты), но парсер к нему не обращается.

**Решение.** Вид стороны определяется ТОЛЬКО через `type`, точно как в
`cTradeObject.init` (`data-sources.md` §2).

**Отвергнуто.** Эвристика «если второе поле не число — значит баф». Она
ломается на бафах без субъекта (`ProductivityBuffLvl3,,1`) и на бафах из двух
полей.

## ADR-2. Строка лота — ровно три сегмента, иначе отказ

**Решение.** `count(explode('|', $offer)) !== 3` → лот не декодируется, счётчик
`unparsed_offers` +1. Третий сегмент (`totalLots`) сохраняется в колонку
`total_lots`.

**Почему.** Клиент делает ровно так: `if (_local_3.length != 3) return`.
Сейчас у нас `< 2`, то есть строка поломанного формата молча даёт мусорный лот.

## ADR-3. Композитный `item_id` вместо новой таблицы сущностей

**Решение.** `item_id` становится композитным строковым ключом
(`adventure:MadHenry`). Для ресурсов формат не меняется вообще.

**Почему.** Все чтение рынка (каталог, аналитика, арбитраж, графики, кэш-ключи,
SPA-фильтры, ссылки) работает через пару `(item_id, target_item_id)`.
Нормализация в отдельную таблицу с FK потребовала бы переписать ~15 сервисов
и весь фронт; риск несоразмерен пользе.

**Следствия.** `item_id` / `target_item_id` расширяются со `string(100)` до
`string(191)`. Разделитель `:` выбран потому, что в игровых именах встречаются
`_` (`ChangeColorScheme_Blue`) и цифры, но не двоеточия.

## ADR-4. Вид и субъект хранятся отдельными колонками

**Решение.** Помимо композитного id денормализуем `item_kind` и
`item_subject` в колонки БД.

**Почему.** Фильтрация по виду должна быть индексируемой. `LIKE 'adventure:%'`
не использует индекс в Postgres без отдельного text_pattern_ops и молча ловит
чужие строки.

## ADR-5. Единица бафа/приключения для цены равна 1

**Контекст.** У бафа есть своё `amount` (например 100 рыбы у
`FillDeposit_Fishfood`), но это НЕ количество лотов, а сила эффекта. У
приключений оно вообще равно 0.

**Решение.** Для бафовой стороны `units = 1`; цена = `costUnits / offerUnits`.
Сырое `amount` бафа пишется в колонку `amount` как справочное значение и не
участвует в арифметике цены.

**Почему.** Деление на 0 и бессмысленные цены вида «1500 монет за одну рыбу из
бафа» — для бафового лота цена осмысленна только «за предмет».

## ADR-6. Лоты без цены сохраняем с `price = null`

**Решение.** `costSide == "@"` → лот пишется, `price` и `target_*` = `null`.
Колонки `price`, `target_amount`, `target_item_id`, `target_item_name`
становятся nullable.

**Альтернатива (отвергнута).** Оставить `continue`. Теряем реальный спрос — а
именно такие заявки часто используются для торговли приключениями.

**Граница.** Все агрегаты цены/арбитража обязаны добавить
`whereNotNull('price')`.

## ADR-7. Классификация — только по протоколу, XML — только справочно

**Решение.** `config/game_tradeables.php` используется для валидации,
метаданных и команды чистки, но НИКОГДА не меняет вид декодированной
стороны (INV-3).

**Почему.** XML из `docs/references/` — слепок одного патча. Новые приключения
появятся в игре раньше, чем в нашем репозитории; классификация по списку
сломается молча.

## ADR-8. Мультисекционный резолвер имён через перебинд контракта

**Решение.** Создаётся `CompositeTradeableNameResolver implements ResourceNameResolver`.
В `app/Providers/MarketServiceProvider.php:34` биндинг меняется с
`GameResourceNameResolver` на новый класс. Интерфейс и все вызывающие места
НЕ меняются.

**Почему.** Контракт `resolve(string $id, string $fallback): string` уже внедрён в
`MarketCatalogService`, `PopularItemService`, `MarketOfferResource`,
`MarketAnalyticsService`. Одна строка в провайдере чинит все четыре места
сразу. `GameResourceNameResolver` остаётся и используется новым резолвером
для ветки `resource` (композиция, не наследование).

## ADR-9. Старые испорченные записи удаляем, а не бэкфиллим

**Решение.** Миграция выставляет всем существующим строкам
`item_kind = 'resource'`. Заведомо испорченные строки (`item_id` = имя
бафа/приключения) удаляются ОТДЕЛЬНОЙ командой с `--dry-run`, а не в
миграции.

**Почему.** Сырые строки лотов не сохранялись, восстановить субъект из
`item_id = 'Adventure'` физически невозможно. Миграции, удаляющие данные,
запрещены конституцией проекта.

## ADR-10. `slot_type` сохраняем, но не фильтруем

**Решение.** Колонка есть, логики нет. В том числе `FRIEND_TO_FRIEND = 4` НЕ
фильтруется.

**Почему.** Нет живого дампа, подтверждающего, попадают ли f2f-лоты в
`GetAvailableOffers`. Фильтр без доказательства может скрыть реальные лоты.

## ADR-11. Обратная совместимость API: только добавление полей

**Решение.** В JSON-ответы добавляются новые поля. Ни одно существующее поле
не удаляется и не меняет семантику, кроме того, что `price` теперь может быть
`null` (ADR-6). Версия API не повышается.

## ADR-12. Фронтенд разбирает id в одном месте

**Решение.** Вся логика имён остаётся в `resources/js/lang/gameNames.js`
(функция `marketItemName`). Компоненты не парсят `item_id` самостоятельно.
Сервер всё равно присылает готовое `item_name`; фронт — второй рубеж для
переключения языка без ресинка.
