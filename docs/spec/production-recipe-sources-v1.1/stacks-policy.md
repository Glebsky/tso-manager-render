# Политика стеков (stacks) — новый раздел, в v1.0 его не было

## 1. Стек против amount

В VO `dTimedProductionVO` есть два разных числа, и путать их нельзя:

- `amount` — сколько единиц в одном стеке. Потолок 25.
- `stacks` — сколько таких стеков ставится в очередь одним заказом. Потолок 200.

Общие лимиты подтверждены владельцем продукта и константами клиента `MAX_PRODUCTION_AMOUNT = 25`, `MAX_PRODUCTION_STACKS = 200`. Остаются как есть.

Но это **глобальные потолки, а не разрешение**. Есть здания, где стеков нет вообще.

---

## 2. Подтверждённые факты

| Здание | Тип | Стеки | Источник факта |
| --- | --- | --- | --- |
| Bookbinder (Переплётчик) | 2 | **нет** | слова владельца + `SkillProductionPanel.Order()` жёстко ставит `amount = 1` и не задаёт `stacks` |
| ChristmasBakery (Рождественская пекарня) | 27 | **нет** | слова владельца |
| SnackStand (Прилавок с закусками) | 18 | есть | работает у владельца |

Тип 2 объясняется кодом клиента. Тип 27 — нет.

---

## 3. Гипотеза H-1 и почему она остаётся гипотезой

У каждого `<TimedProductionList>` в GLOBALS есть атрибут `type`. Расклад по 71 списку:

| Значение `type` | Списков |
| --- | --- |
| `timedproduction` | 29 |
| `culturebuilding` | 23 |
| `simpleproduction` | 9 |
| атрибута нет | 10 (9 пустых списков плюс список 5) |

Сопоставление с фактами выше:

- ChristmasBakery = тип 27 = `culturebuilding` → стеков нет
- SnackStand = тип 18 = `simpleproduction` → стеки есть

**Гипотеза H-1:** списки с `type="culturebuilding"` не поддерживают стеки.

Выглядит правдоподобно: культурные здания дают городской эффект, а не товар на склад, и штабелировать их бессмысленно.

**Но это одна точка данных против одной.** По иерархии источников истины из v1.0 это ранг «догадка», а догадки запрещены как основание для жёсткого поведения в коде.

---

## 4. Решение: конфиг, а не автоматика

Не выводи право на стеки из атрибута XML в коде импортёра. Сделай это явной картой в конфиге, которую человек может поправить за тридцать секунд, не перезапуская импорт.

Файл `config/game_production_sources.php`, новый ключ:

```php
'stacks' => [
    // Потолки из клиента. Не менять без доказательств.
    'max_amount' => 25,
    'max_stacks' => 200,

    // Типы, где stacks всегда 1. Каждая строка обязана иметь
    // комментарий с основанием. Без основания строку не добавлять.
    'unsupported_types' => [
        2  => 'SkillProductionPanel.Order() жёстко amount=1, stacks не задаётся',
        4  => 'CollectionProductionOverlay не имеет степпера стеков',
        27 => 'Подтверждено владельцем продукта в игре',
    ],

    // Гипотеза H-1. ВКЛЮЧЕНА по умолчанию, так как ложный запрет
    // дешевле ложного разрешения.
    'disable_for_list_type' => ['culturebuilding'],
],
```

Обоснование консервативного дефолта. Ошибка в сторону запрета даёт видимое ограничение в интерфейсе, о котором легко сообщить. Ошибка в сторону разрешения даёт запланированную на ночь таску, которая молча отваливается на сервере — ровно та боль, с которой началась эта задача.

## 5. Вычисление поля `stacks_supported`

На этапе импорта каждый рецепт получает булево поле `stacks_supported`. Порядок правил строго такой, первое сработавшее побеждает:

1. тип есть в `unsupported_types` → `false`
2. тип пришёл из источника `skillpoints` или `collections` → `false`
3. `type` списка есть в `disable_for_list_type` → `false`
4. иначе → `true`

Правило 2 дублирует строки 2 и 4 из конфига намеренно: если кто-то очистит `unsupported_types`, защита останется.

Вместе с `stacks_supported` вычисляется `max_stacks_per_order`: если `stacks_supported === false`, то 1, иначе 200.

Аналогично для `max_amount_per_order`: для источника `skillpoints` он равен **1** (клиент жёстко шлёт `amount = 1`), во всех остальных случаях 25.

---

## 6. Влияние на политику заказа

Политика `ProductionOrderPolicy` сохраняет 11 шагов и причины отказа `amount_exceeds_recipe_limit` и `stacks_exceeds_recipe_limit` без изменений — просто теперь лимиты в рецепте бывают равны 1.

Новая причина отказа НЕ добавляется. Не плоди сущности.

---

## 7. Влияние на UI

В `ProducerPicker.vue`:

- если `stacks_supported === false` — поле стеков **скрывается полностью**, а не блокируется. Заблокированное поле со значением 1 выглядит как баг;
- аналогично для поля количества при `max_amount_per_order === 1`;
- если скрыты оба поля, показать пояснение по ключу `tasks.production.single_item_only`.

Переводы в проекте уже есть — добавь недостающие ключи во все три локали: `en`, `ru`, `uk`. Не оставляй английский текст в русском файле как заглушку.
