# AGENTS.md

## О проекте

Менеджер аккаунтов The Settlers Online. Работает **без запуска игрового
клиента**: реверс-инжиниринг оригинального протокола игрового сервера,
собственные HTTP-запросы, headless-выполнение игровых команд.

Состав:
- **Backend**: Laravel 10 — API для SPA + слой игрового протокола.
- **Frontend**: SPA на Vue 3 + Vite — веб-панель (данные аккаунта, ресурсы,
  управление задачами).
- **Мультиаккаунт**: пользователь может подключать несколько игровых
  аккаунтов; вся логика сессий/команд всегда работает в контексте
  конкретного аккаунта.

Реализовано: получение информации аккаунта (кроме друзей), остановка
производства. В планах на этой же основе: бафы зданий, отправка
специалистов (геологи/исследователи), друзья.

Референс по семантике игровых команд и модели данных игры:
https://github.com/fedorovvl/tso_client (userscripts, mapping).

## Стек

- PHP 8.1 (не использовать синтаксис 8.2+: readonly-классы целиком,
  константы в трейтах и т.п.; enum'ы и readonly-свойства — можно)
- Laravel 10, PostgreSQL, Redis (кэш, игровые сессии, очереди)
- Vue 3 + Vite (SPA), взаимодействие с backend только через JSON API
- Тесты: PHPUnit, Laravel Pint, Larastan

## Архитектура backend

В основе проекта лежит строгое разделение слоёв с соблюдением принципа инверсии зависимостей (Dependency Inversion Principle - DIP). Зависимости направлены исключительно внутрь, к доменному слою.

## Структура директорий `app/`

### 1. Транспортный слой (HTTP)
*   **`Http/Controllers/Api/`**
    Тонкие контроллеры. Отвечают исключительно за прием HTTP-запроса, делегирование валидации и вызов нужного сценария (Action).
    *Workflow:* валидация (`FormRequest`) → вызов `Action` → формирование ответа (`JsonResource`).

### 2. Слой приложения (Application Layer)
*   **`Actions/`**
    Use-cases (сценарии использования) приложения. Реализуют бизнес-логику на уровне взаимодействия системы с пользователем. Строгое правило: один класс = одно действие (Single Responsibility).
*   **`Jobs/`**
    Асинхронные задачи. Обрабатывают игровые команды, отправляемые в очередь (сгруппированные и выполняемые строго per-account для избежания конфликтов состояния).

### 3. Доменный слой (Domain Layer)
*   **`Game/`**
    Ядро бизнес-логики. Здесь сосредоточен весь игровой протокол. Этот слой **полностью изолирован от фреймворка Laravel** (не зависит от инфраструктурных компонентов).
    *   **`Client/`** — Содержит `GameClientInterface` и конкретную реализацию реверснутого протокола для взаимодействия с игровым сервером.
    *   **`Protocol/`** — Низкоуровневая логика сериализации и десериализации пакетов/данных протокола сервера.
    *   **`Commands/`** — Игровые действия, реализованные через паттерн Command (например: `StopProduction`, `BuffBuilding`, `SendSpecialist`).
    *   **`Session/`** — `SessionManager`. Управляет жизненным циклом сессии игрового аккаунта: логин, работа с токенами, их обновление (refresh). Ключи сессий хранятся в Redis со строгой привязкой к `game_account_id`.
    *   **`DTO/`** — Data Transfer Objects (объекты передачи данных) для запросов и ответов. *Строгое правило:* никаких нетипизированных массивов для передачи данных между слоями, только DTO.
    *   **`Enums/`** — Строгие перечисления: коды команд, типы ресурсов, статусы процессов.
    *   **`Exceptions/`** — Специфичные доменные исключения (например: `SessionExpired`, `GameServerError`, `ProtocolError`).

### 4. Инфраструктурный слой (Infrastructure)
*   **`Models/`**
    Инфраструктура базы данных. Содержит модели Eloquent ORM (`User`, `GameAccount` и т.д.).

### Правила слоёв (нарушать нельзя)

- Контроллеры не содержат бизнес-логики и не ходят в HTTP игры.
- Весь исходящий HTTP к игровому серверу — только внутри `app/Game/Client/`.
- Код приложения зависит от `GameClientInterface`, не от реализации.
- Каждая игровая команда — отдельный класс в `app/Game/Commands/` с общим
  интерфейсом. Новая команда (баф, отправка специалиста) = новый класс по
  образцу `StopProduction`; существующие классы не изменяются (OCP).
- Разбор ответов сервера — только в `app/Game/Protocol/`. Наружу отдаются
  DTO, «сырые» структуры протокола не покидают слой `Game`.
- API-ответы для SPA — только через `JsonResource`, не сырые модели/DTO.

## Мультиаккаунт (важно)

- Любая игровая операция принимает `GameAccount` явно — никаких
  «текущих аккаунтов» в глобальном состоянии/сессии PHP.
- Ключи Redis для игровых сессий: `game:session:{game_account_id}:...`.
- Джобы игровых команд сериализуют id аккаунта; очередь/троттлинг —
  на каждый аккаунт отдельно, чтобы аккаунты не блокировали друг друга.
- Все API-эндпоинты проверяют, что аккаунт принадлежит текущему
  пользователю (Policy).

## Игровые сессии и надёжность

- Сессии/токены — в Redis с TTL. Протухшая сессия → автоматический
  re-login внутри `SessionManager`, вызывающий код об этом не знает.
- Игровые команды выполняются через Jobs с retry + exponential backoff.
- Rate limiting обязателен: `Redis::throttle()` на исходящие запросы,
  отдельный лимит на каждый игровой аккаунт. Запросы в цикле без
  троттлинга запрещены.
- Логировать запросы/ответы игрового сервера в отдельный канал `game`
  с маскировкой паролей и токенов.

## Принципы кода

- SOLID, DRY, KISS. Абстракции только на границах (HTTP игры, протокол,
  хранилище сессий) — не создавать интерфейсы «на будущее».
- `declare(strict_types=1);` во всех файлах, полная типизация.
- Никаких магических строк/чисел — enum'ы и `config/game.php`.
- Ранние возвраты вместо вложенных if; методы < ~25 строк.
- Доменные исключения из `app/Game/Exceptions/`, не `\Exception` напрямую.
- Не оборачивать Eloquent в репозитории без реальной необходимости.

## Frontend (Vue 3 + Vite)

- Composition API + `<script setup>`. Логика запросов к API — в
  composables/сторах, не в компонентах.
- Один источник правды по состоянию аккаунтов/ресурсов — [Pinia]-стор.
- Компоненты не знают про игровой протокол — только про JSON API backend'а.
- Типы ответов API держать в одном месте и синхронизировать с
  `JsonResource` backend'а.

## Тесты

- Новый код — с тестами; существующие тесты должны проходить.
- Игровой сервер в тестах мокается через `Http::fake()` с реальными
  примерами (фикстурами) ответов протокола. Живые запросы к серверу
  игры в тестах запрещены.
- На каждую игровую команду: тест сериализации payload + тесты обработки
  ответа (успех / протухшая сессия / ошибка сервера).
- На парсеры протокола (`app/Game/Protocol/`) — юнит-тесты на фикстурах.

## Что агенту делать нельзя

- Изменять реверснутый формат протокола/эндпоинты без явного запроса —
  формат подтверждён реальным трафиком, «исправление» его ломает.
- Коммитить секреты, учётные данные игровых аккаунтов, токены (только `.env`).
- Отключать rate limiting, retry или маскировку данных в логах.
- Делать широкие рефакторинги вне поставленной задачи.
- Хранить пароли игровых аккаунтов в открытом виде (только encrypted casts).
